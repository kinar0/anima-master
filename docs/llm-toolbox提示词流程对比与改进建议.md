## 1. 最重要的判断

值得引入本插件的是 Toolbox 的“分类浏览 + 中文语义释义 + 易混标签辨析 + 按需手册”，以及输出字段的明确作用域。

本插件应保留 LLM1 的原文意图抽取、身份与服装来源分离、逐角色 WardrobeAuthority、稳定外貌维度权限。Toolbox 的工具循环不能替代这些能力。

建议逐步形成：原文意图 → 本地权威证据 → 有作用域的语义检索 → 逐角色画面计划 → 后端输出。先消除提示词契约冲突和名词全局补入问题，再引入检索，最后统一 Anima 与 NAI 的输出计划。

这些是架构判断。尚未调用真实 LLM 或生成图片，没有将“设计合理”写成“已经证明画质更好”。

## 2. Toolbox 实际如何规划

### 2.1 它不是两个固定 LLM 阶段

主入口是 `src/main/llm/runner.ts::runLlm`。它运行一个有上限的工具交互循环：

```text
用户指令 / 可选现有参数
  → 准备标签数据与可用工具
  → 组装 system 与 user 消息
  → 模型选择检索工具
  → 本地检索结果回传模型
  → 可继续检索，也可调用参数输出工具
  → 画风覆盖与 NAI 参数规范化
  → 回填工作区
  → 用户生成，或开启自动生成后直接生成
```

默认 `maxToolRounds=10`，这是上限，不是每次必跑十轮。`autoSkipSearch` 默认关闭。

工具包括：

| 工具 | 实际职责 |
| --- | --- |
| `search_tags` | 字面检索角色、画师、作品和通用概念，返回候选、分数及可选释义/特征 |
| `browse_tags` | 浏览分类内标签，让模型看中文释义挑选 |
| `load_tag_manual` | 读取某主题的完整标签手册 |
| `generate_image` | 返回单图参数，供回填 |
| `generate_image_characters` | 返回全局参数与角色数组，供回填 |

这里的生成工具名来自上游插件，但在本工作台中，调用它们并不立即请求 NovelAI；图片生成由另一个生成模块负责。

同轮同时提出检索和生成时，runner 执行检索，将生成调用回复为“请先完成标签查询后再调用此工具”，继续下一轮。最后一轮仅提供生成工具，但代码没有因此保证模型必然调用；模型没有给参数时返回 `noParams`。多个生成调用只采用第一个。

### 2.2 系统提示词是组合出来的

`src/main/llm/prompt.ts::buildSystemPrompt` 的顺序为：

1. 配置中的 `systemPrompt`，初始默认来自 `resources/prompts/system.md`。
2. 多角色动态说明，含 `naiCharSystemPrompt`。
3. `tag-skill-core.md` 的检索规则。
4. 启用时的主题手册目录。
5. 可用时的标签分类目录。
6. 启用修改模式时的局部修改规则。

`tail.md` 走独立的尾部注入逻辑，不是上述常驻 system 的一部分，默认关闭。OpenAI 兼容路径追加末尾 system 消息；Claude 路径在最后 user 内容块追加文本。这里只描述实现，不建议移植其中与提示词质量无关的拒绝限制文案。

基础 system 按“提取 → 构图裁切 → 场景具象化 → 查询 → 一致性检查 → 输出工具”组织。它强调用户要求优先、取景框外信息应省略、同维度不要冲突、显式权重保留，并专门描述 NAI 的画师、权重与文字语法。

值得借鉴的是规则按阶段和后端分类。其规则仍有不一致处，例如检索工具描述写“≥0.85 直接采信”，后加的 skill-core 却要求 0.85–0.95 核对释义。目录说明也仍有“search 没查准再 browse”的旧口径。因此不能仅因为它采用模块化提示词，就认为其全部契约已经一致。

### 2.3 为什么分类浏览比增加中文别名更有价值

`src/main/tagdb/browse.ts` 中，keyword 只排序，不过滤。字面未命中时仍返回该分类内容，避免把模型真正要找的概念删掉。匹配面可包含标签、中英日别名和 Wiki 文字，但回传主要是 tag 与精简中文释义。

例如“从上往下看”可能表达相机俯视，也可能表达人物低头。分类与释义能帮助区分 `from_above` 和 `looking_down`；字符串相似度本身没有相机/人物这个语义作用域。

默认每页预算 12000 字符，同时至少返回 30 条。这是软字符预算，不是严格 token 上限；有长释义时仍可能超过预算。多轮历史又会重复携带已有工具结果。因此本插件可借鉴检索语义，但不宜直接复制整类返回量和默认十轮上限。

### 2.4 释义层主动纠正“模型以为自己知道”的词

`src/main/tagdb/gloss.ts::buildInjectionBlock` 对输入中的标签样式片段扫描，注入字面误读提醒与废弃提醒，默认最多 20 项。中文句中嵌入的多词英文 tag 也有补捞；普通中文词和单个英文自由文本不会一概当 tag 查。

Release 中的实例：

| 标签 | 数据中的解释 |
| --- | --- |
| `deep_skin` | 手指抓握时深陷皮肤，不是深色皮肤 |
| `cowboy_shot` | 含头部的大腿以上构图，与牛仔题材无关 |
| `comic` | 多格连环画形式，不是喜剧 |
| `indian_style` | 盘腿坐姿，与印度服饰无关 |
| `hairband` / `headband` | 区分头顶发箍与额头束带 |

本插件现有名词翻译是“中文触发词 → canonical tag”，不能完整承载这些释义、误读与辨析信息。两种数据应分开保存和使用。

### 2.5 输出结构与多角色作用域

全局十字段是 `count/style/character/artist/appearance/tags/environment/series/nltags/quality`；角色五字段是 `count/character/appearance/tags/nltags`，另有角色负面词与位置参数。

多角色时，全局负责总人数、构图、场景、风格；角色块负责身份、外貌、服装、动作和表情。角色 count 要求 `girl/boy/other`，全局 count 写数量。顶层 nltags 不重复角色自身外貌，各角色 nltags 描写自己。

这种结构让归属直接存在于数组中，比在一长串自然语言中寻找角色名字更容易消费。不过其 schema 并非全面严格验收：单图只 required `tags`；多人只 required `tags/characters`，提示词中“必填”的 nltags 等并没有全部变成硬结构规则。工具调用也不自动证明内容正确。

### 2.6 收口及修改模式

`fill.ts::postProcess` 的处理包括画风锁定、NAI 规范化、透明背景、负面词兜底、比例转宽高，然后回填。`nai.ts::finalizeArgs` 会处理画师前缀、LoRA、角色数与误放的全局字段。它不具备本插件的服装来源、陈旧衣柜、用户修改优先级裁定。

“在现有内容上修改”把当前工作区序列化成与输出工具相同的形状，再要求模型完整输出、只改明确要求的部分。它每次仍是新对话，没有自动累积聊天记忆。修改保真主要依赖模型遵守提示，主机没有通用的局部差异合并机制。

服装状态有八个独立分类：敞开未扣、未穿缺失、开口镂空、掀拉移位、浸湿透视、破损脏污、滑落走光、紧绷宽松。这种“衣物品类”与“衣物状态”分离，很适合本插件的 remove/damage/add/recolor 语义。

与当前可读的本地 `anima-1.0.csv` 精确 canonical 名称对比，17209 个分类标签中有 16076 个存在，1133 个未找到；释义库中有 16107 个存在，1135 个未找到。这里未执行别名重定向，未找到不能直接等同于模型不支持，但足以说明必须适配当前标签库，不能全部提升为 Anima hard tags。

画师比较还必须归一 `@` 与 NAI `artist:` 等显示语法，不能用未经归一的集合差直接判断覆盖率。

### 数据质量不能与“官方权威”混为一谈

特征 CSV 只有 character/copyright/appearance/clothing 四列，没有逐条来源、样本支持度或人工核验状态。代码将其称作官方特征，但当前数据结构不足以证明每条都是官方设定。

例如初音未来的 appearance 同时含 aqua/blue 的发色与瞳色、long/very_long 的长度，并有 hair_ornament、bare_shoulders；服装也含 sleeveless 与 long_sleeves 等组件。这些可能来自颜色近义、不同造型或组合衣物，不能简单视为同一当前造型的一组互斥权威值。

此外 `togawa_sakiko_(master_of_melodia)` 在 Toolbox 索引中位于 characters，并在特征表中有造型组件；本次 Anima CSV 将其列为 general。这里不判断远端最新分类谁对谁错；这说明在本插件中必须继续按精确来源和本地分类决定“可见身份”还是“服装来源”，不能因为外部库叫它角色就建立可见角色。

默认 `tagQueryCharacterClothing=false`，角色服装富化是可开启能力，不应误写成默认始终注入。

## 4. 与本插件的主要异同

| 方面 | Toolbox | 本插件 |
| --- | --- | --- |
| 用户入口 | 工作区指令，可人工审阅后出图 | 聊天命令，通常自动提交与回传 |
| 规划 | 同一对话中的多轮检索与参数输出 | LLM1 意图抽取、本地裁定、LLM2 写作；部分路径追加调用 |
| 标签理解 | 分类、释义、手册、字面候选 | 本地 resolver、角色/衣柜证据、配置名词映射 |
| LLM1 边界 | 无独立意图阶段 | 只输出原文角色、衣物、来源、修改，不猜 tag |
| 服装与稳定外貌 | 同在 appearance，主要交模型决定 | 分开存储，逐角色服装与逐维度外貌裁定 |
| 多角色 | 直接输出角色数组 | 普通七字段中的角色描述；NAI -r 再规划角色实例 |
| Nltags | 中文完整描述，依后端设计重复展开 | 英文补充，最终去除与 Identity/Details 重复内容 |
| 修改已有内容 | 工作区完整参数与局部修改要求 | 图生图/参考上下文、逐角色衣物与外貌 patch 等 |
| 出错回退 | 工具与接口修复；无参数不回填 | 意图修复、未解析状态、写作格式修复、权限过滤 |
| 后端 | NovelAI | Anima/ComfyUI，加 NAI 自定义工作流 |

两者都让用户要求高于资料，都做结构化输出和本地规范化，也都不能靠提示词独自保证语义正确。区别在于 Toolbox 更擅长给模型可读的词汇知识；本插件更擅长维护“这条证据属于谁、何时失效”。

本插件的完整消费者链仍是：命令分发 → 生成任务拆手工尾缀/参考上下文 → PromptPipeline → LLM1 → 角色与标签证据 → WardrobeAuthority/外貌权限 → LLM2 → 后处理/最终拼接 → 工作流提交/历史/下载 → 聊天交付。

raw/关闭优化不走普通权限；`#` 手工尾缀在构建后原样插回；旧 `/anm 多人` 在普通 LLM1 前分流；NAI `-r` 以普通完整提示词为基础再规划可见实例。改进必须分别保留这些契约，不能只测普通单人。

## 5. 本插件当前值得先改的实现问题

### 5.1 第二阶段任务书与 system 的契约冲突

`prompt_pipeline.py` 第二阶段 system 要求“只输出英文 danbooru tags，用英文逗号分隔”，但同一 system 后面要求七个花括号字段，模板又明确 Identity/Details/Nltags 是完整自然语言。这不是单纯文风差异，是输出协议冲突。

`prompt_templates.py` 允许 Nltags 对全画面完整重述，后处理 `strip_structured_block_duplicates_from_nltags` 却按规范化句子去重。因此模型会花预算生成随后被删的内容，也可能以不同措辞重述并绕过去重。

背景也有实际漂移：模板和追加背景规则禁止未要求时新增地点；`docs/prompting.md` 的默认自由创作及后处理 `generated_scene_selected` 又允许保留模型设计的具体场景。应根据期望产品行为选择一个口径，同时统一 system、模板、背景策略、文档和测试。

优先做一次提示词契约清理，不能通过再加一段“优先级最高”无限叠加规则解决。

### 5.2 名词翻译仍可能在全局补入角色专属条件

在约 6976 行的 `missing_term_tags` 逻辑中，经过权限过滤的映射若未出现独立 tag，结构化路径会把它加到共享 `structured_extra_tags`。

“爱音穿芭蕾舞裙，祥子穿西装”中，writer 即使已经在爱音 Details 自然语言表达舞裙，仍可能全局补一个 `tutu`。标签存在与穿着者正确是两件事；这种补入无法仅靠扩大翻译词库修好。

NAI -r 已把遗漏名词 tag 降为诊断，但它在普通完整提示词之后运行，不能反过来证明上游全局补入是安全的。

### 5.3 NAI -r 的第二次完整写作增加漂移机会

当前先写并过滤普通七字段，再调用布局 LLM 重写全局与角色提示词。布局任务书确实很完整，允许原文覆盖前一阶段已合并的实例差异；但后置处理主要执行特定修正（例如 appearance omit、cosplay、全局误放项、画师恢复），没有在该位置完整复用普通路径的服装权限与所有外貌维度合并。

这是可核实的架构风险，不是本次已经复现的生图错误。应让布局阶段尽量只补实例关系与位置，并让最终输出统一通过权限裁定。

## 6. 推荐的落地次序

| 优先级 | 改动 | 收益与边界 |
| --- | --- | --- |
| P0 | 统一 system/模板/背景/Nltags 契约 | 减少写作冲突与无效 token，不增加模型调用 |
| P0 | 名词映射携带角色/实例作用域 | 修正全局补入污染，不靠单个服装特例 |
| P1 | 增加释义、误读、辨析数据层 | 可先注入已有 tag 的少量解释，不改变 LLM1 的职责 |
| P1 | 分类检索与有预算的证据包 | 改善一般动作、姿势、材质与镜头词的语义选择 |
| P2 | 统一逐角色画面计划与后端输出 | 减少 -r 从扁平文本重新猜归属 |
| P2 | 来源记录与请求级诊断 | 分清词汇命中、语义绑定、模型输出和最终删改 |
| P3 | 可选工具循环与局部修改快照 | 对复杂请求扩展；普通请求保持轻量 |

### 6.1 最先实现一个有归属的概念记录

建议内部概念记录至少保存：原文片段及位置、concept kind、polarity、目标角色/实例或 global/unresolved、canonical 候选、词汇证据、语义绑定来源。

LLM 输出可以继续用原文实体短语，ID 由宿主分配。不要把内部枚举、tag 猜测和大量交叉引用重新塞回 LLM1。

绑定明确的舞裙只进入爱音的角色输出；明确共享要求展开到每个目标；歧义保留原文和 unresolved，不能补给所有人。标签字典只证明词汇含义，不证明某个人穿着它。

### 6.2 检索先采用宿主准备证据，之后再评估工具循环

第一版可以保留当前调用形态：宿主根据已有衣物/修改/外貌原文和有限的概念意图，读取相关分类、释义、辨析，组装紧凑证据包给 writer。必要时增加一个独立、受限的概念路由步骤；不要为了覆盖全部语义把现有 LLM1 一次扩成巨型协议。

候选包需要标签、含义、相近词区别、来源和所属作用域；分类 keyword 只排序的原则值得保留。每请求应有总候选/字符或 token 预算、查询去重和缓存，不必让每个请求读取整个手册。

本机 AstrBot `Context.llm_generate` 接受 tools，但不会自动执行工具；另有 `tool_loop_agent`。如果后续做模型主动检索，应优先适配已有 provider 与工具能力，核对 provider 支持和 runner 参数传递；不必直接移植 Toolbox 的整套 HTTP 客户端。

可试验最多 1–2 次检索往返，加一次针对具体问题的修复。结束条件应看请求所需概念有没有可用证据，不能用“本轮最高字面分全部 ≥0.85”代替完整覆盖。

### 6.3 逐角色计划作为两种输出的共同来源

中期目标是保存 scene/camera、角色身份、每个可见实例的衣物/外貌/动作、关系边，以及各事实的来源与权限。

Anima 输出器将其转换为标签与有归属的英文描述；NAI 输出器转换为 base prompt、角色提示词、关系动作和坐标。布局模型可以提出构图和坐标，不必重新发明已有身份、衣服和外貌。

同一身份出现在多个格子时，要有不同 instance ID；衣柜 owner、服装 donor 和 visible instance 分别存在，不能用一个 canonical 名称代替全部关系。

可以先在现有七字段结果旁保存结构化对象，让 -r 消费这些对象，而不一次废除全部七字段、旧多人和 raw 兼容入口。

### 6.4 后端语法独立，不能直接照抄 NAI system

Toolbox 使用 NAI 权重、artist 前缀和未转义圆括号，本插件当前 `display_tag_text` 使用 Anima/ComfyUI 显示规则。NAI 自定义工作流还会经 `ComfyUIToNovelAIV4` 转换节点，角色框也创建该转换节点。

因此差异不等于现有 NAI 接入必然错误，不能盲目删转义或全局替换权重。更合理的是中间计划保存 canonical 与明确权重意图，由实际工作流适配器选择输出语法，明确哪些转换已由节点承担。

NAI 中文自然语言、text 强化、多角色动作语法也不应成为所有 Anima 请求的共用规则。最终生图提示词的 token 预算与 LLM 输出 max_tokens 分别计算；仅增加 LLM 输出预算并不能保证生成端读完所有条件。

### 6.5 资料有效性、语义正确性与输出位置分开记录

建议诊断至少能区分：

- vocabulary_valid：词库存在、未废弃或有配置证据；
- request_grounded：原文有相应正向要求，且目标归属可追溯；
- emitted：最终实际输出到哪个角色或全局；
- dropped_reason：用户删除、画外、陈旧衣柜、冲突、其他人的条件等。

本插件已经有丰富任务摘要，下一步是把证据到最终输出的关系连起来，而不是再堆更多孤立标签列表。可以借鉴 Toolbox 的内容快照与来源指纹，但不必引入其完整工作台。

## 7. 不建议照搬的部分

1. 不把检索相似度当语义置信度，也不把模糊角色命中直接当已确认身份。
2. 不把外部角色特征 CSV 当完整权威档案，更不能用它覆盖人工衣柜或外貌。
3. 不要求所有请求都写四段完整重述。应根据后端和角色数控制有效信息预算。
4. 不采用“强制每人瞳色”的规则覆盖不可见要求；本插件的 omit 权限更精细。
5. 不把普通借衣与 cosplay 等同。Toolbox 的通用提示会要求两者都加 cosplay tag；本插件只对明确 cosplay 加标签的边界更合适。
6. 不把“调用工具”视为格式或语义验收已经完成；最终仍要检查结构、实例与权限。
7. 不恢复完整衣柜硬注入。查到组件是证据，不代表本次全部可见或应输出。

## 8. 验收建议与本次验证范围

建议后续改动覆盖以下成对案例：

- 俯视镜头 / 人物低头：分别检查 camera 与 gaze。
- 一人舞裙另一人西装 / 两人都穿舞裙：验证独占与共享归属。
- 没穿外套 / 外套破损：验证 remove 与 damage 不混淆。
- 不画眼睛 / 闭眼或无高光：验证 omit 边界。
- 穿某人的衣服 / cosplay 某人：验证来源身份与 cosplay 的区别。
- 制服在场景中出现 / 明确某人穿制服：避免场景误绑定。
- 同一角色两格不同衣物动作：实例不能合并。
- 中文含英文 tag / 普通中文里偶然出现英文词：验证释义扫描不误报。
- 未指定场景 / 明确白底 / 明确暗室无光源：验证自由创作边界一致。
