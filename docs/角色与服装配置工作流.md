## 总览

| 数据源 | 主要解决的问题 | 是否可绑定角色 | 最终用途 |
| --- | --- | --- | --- |
| `danbooru_character_alias_mappings` | 用户说的名字对应哪个 canonical 角色 tag | 是，形成角色 anchor | 角色身份识别与消歧 |
| `fixed_characters` | 原创、冷门或容易画错的角色有哪些稳定身份信息 | 取决于工作流 | 结构化路径中的身份提示；多人/旧路径中的较强约束 |

| 服装套组 | 某个完整命名套装对应哪个 canonical outfit tag | 是，形成 outfit anchor | 角色级完整套装约束，可附带验证过的组件档案 |
| 名词翻译 | 用户出现某个词时必须加入哪个 tag | 否 | 全局 hard tag |

## 当前提示词工作流

普通 `/anm` 优化请求大致经过以下步骤：

1. 主机从用户原文预取固定角色、角色别名、服装套组、名词翻译和已经保存的角色视觉档案；这些内部数据不会作为枚举题塞给 LLM1。
2. 第一阶段语义规划 LLM 只负责理解请求：输出 `characters` JSON，每个角色给出 `name / aliases / clothing / clothing_source / clothing_changes / appearance_changes`；未知别名使用空数组，未知衣服使用 `null`，证据必须原样来自用户请求。可见角色不得合并、抽样或省略；宿主最多保留 22 人。原文明示“6 个角色 / 六人 / 4girls and 2boys”等人数时，任务书会写入精确数组长度契约，返回数量不符会触发一次结构修复。`双方 / 两人 / 都 / 双女主 / both / all` 等共享范围必须展开到每个穿着者。
3. LLM1 不生成 tag、candidate、lookup、wardrobe kind、ID、group、description 或交叉引用。它把角色名限制为原文中的实体短语，并用独立 `aliases` 数组声明与该实体明确配对的括号别名。主机只有在原文中再次验证 `name（alias）` 或反向形式精确相邻后，才生成未验证角色 anchor；不会再从括号左侧贪婪截取角色名。LLM1 的任务书会完整列出服装修改槽位：`upper_body.primary / lower_body.skirt / one_piece.dress / outerwear / headwear / face_accessory.mask / handwear / legwear / footwear / lower_body.all / misc`，不好分类的组件必须使用 `misc`。主机同时兼容常见时态操作和日常槽位名，把未知非空槽位归入 `misc`；无法通过原文证据、操作或颜色校验的修改会触发一次带具体原因的修复请求并写入调试摘要，不再无提示过滤。随后主机把其余可读字段转换成内部 anchors/wardrobe 状态，再匹配本地角色档案、命名衣柜和词库。校验不要求猜测 tag；明确的 cosplay 关系和逐角色删除/换色可由主机从原文保守补齐，避免让 LLM2 猜归属。旧版 candidates/lookups、wardrobe 枚举和复杂 anchors/character_plans JSON 继续只作为兼容输入。
4. 第一阶段规划不再由 Danbooru 工具是否可用决定。即使本地查询临时不可用，也必须先提出角色与服装关系；查询可用时再验证候选和补充档案。
5. 每个目标角色最终得到一个关系状态：`resolved` 表示 LLM1 给出了可接受关系；`explicit_but_unresolved` 表示原文明确含服装意图、但该角色没有可接受绑定；`unspecified` 表示该角色没有实际服装基础，或只有增删/换色要求却没说明基于哪套衣服修改。
6. 缺省衣柜按角色决定，不按整条请求一刀切。A 明确穿婚纱而 B 没说穿什么时，A 的 default 禁用，B 的 default 仍作为软参考交给第二阶段；B 在普通合影中应更倾向沿用，在泳池边等强场景中可结合情境替换或补全。A、B 分别明确穿连体式和分体式泳装时，两人都有实际服装基础，因此都不读取 default。
7. 程序构建请求级 `WardrobeAuthority`，集中记录 `cached_tags`、`explicit_tags`、`selected_tags`、`source_grounding_tags`、`unbound_grounding_tags` 和 `stale_cached_tags`。它只执行证据优先级、用户删除和角色所有权过滤，不替第二阶段解释完整语义。
8. 有角色级计划后，旧的请求级 `outfit_summary` 会被标记为 `suppressed_by_character_authority`，不能作为第二套服装来源继续注入。
9. 第二阶段 prompt writer 输出 `Count / Characters / Copyright / Identity / Details / Tags / Nltags`；它同时收到完整原文、逐角色稳定外貌、已解析关系、可信服装下限、未绑定证据和 stale 默认衣柜。它负责最终角色绑定、服装补全、动作、外貌、位置、构图、镜头和氛围。主机只硬校验七字段外壳和人数锚点；Identity/Details 通过角色名唯一出现、明确段首和前一角色继承来尽力划分作用域，无法归属的补充片段保留到 Nltags，不因自然语言句式复杂而丢弃。
10. 后处理使用同一个 `WardrobeAuthority` 清理共享 Tags、角色 Details、Nltags、`required_profile_tags`、`required_core_tags` 和最终结构化 tags；Identity 则按“角色 × 外貌维度”合并，防止 LLM 猜测覆盖未被用户修改的稳定特征。
11. 最后才拼接人数、角色、质量词、画师词、画风和背景控制词并提交 ComfyUI。

## 四个组件的关系

| 组件 | 输入 | 输出 | 权限边界 |
| --- | --- | --- | --- |
| 第一阶段 LLM（semantic planner） | 用户原文 | 逐角色可读意图字段 | 只分析谁出现、谁穿什么、来源与修改；不看内部枚举、不猜 tag |
| 角色数据库/视觉档案 | 角色别名、canonical tag、历史证据 | 稳定 `appearanceTags` 与 default/casual/stage 等候选衣柜 | 只提供资料；缓存衣柜不会因为角色被识别就自动生效 |
| `WardrobeAuthority` | 第一阶段建议、用户显式证据、角色衣柜 | LLM2 上下文、未绑定证据、stale/removed tags 与角色所有权 | 只处理数据优先级和确定冲突；不会把数据库组件追加成最终 hard tags |
| 第二阶段 LLM（prompt writer） | 完整原文、角色身份、可信/未绑定证据和禁止恢复项 | 七字段英文画面描述 | 最终解释角色绑定并完成服装、动作、外貌、位置、构图、镜头与氛围 |

稳定外观与衣柜是两条独立数据：切换婚纱、私服或演出服时，角色的发色、瞳色、角、耳朵等 `appearanceTags` 仍会保留；default 校服等 `outfit tags` 只有被本次 wardrobe 计划选择才会保留。

本地已确认的 owner 身份必须绑定回可见角色 anchor，即使查询没有再次命中。LLM2 上下文明确列出原文名字与 canonical 名的对应关系；后处理先保留精确匹配，再处理唯一可确定的改名。完整角色清单只剩一名未知与一个缺失身份时，可替换其名字并同步改写 Identity、Details、Nltags；多名未知不按位置分配。仍缺失已确认可见身份时，要求 LLM2 重写一次，失败则停止。衣柜 donor/source 不因此升级为可见角色，匿名且没有已确认身份的请求仍允许 Characters 留空。

### 两类服装档案的硬边界

持久化层明确区分两种实体，不能再用同一条 `character_outfit` 同时表达：

- `character_outfit`：属于某个角色或人格的衣柜变体。`source_tags` 必须是角色/persona canonical tag；`default / casual / summer / winter / stage` 只在该角色被点名时选择，同时可携带该角色的稳定外貌。
- `named_outfit`：可由任意角色穿着的通用命名套组。它独立保存 `canonical_tag`、`variant`、触发别名和 `component_tags`，没有穿着者身份，也不保存角色外貌；LLM1 抽出的服装原文精确命中别名后，主机把套组 anchor 绑定给对应穿着者。

Danbooru 有独立服装词条的校服、制服和完整套组属于第二类。例如“羽丘冬季校服”是 `haneoka_school_uniform + winter` 的通用套组，高松灯、千早爱音或其他角色都可以选择它；它不是“高松灯的 winter 角色档案”。“千早爱音的演出服”这类由 `chihaya_anon + stage` 取得的本人变体才属于第一类。

旧缓存曾把通用套组采样结果写成 `character_outfit`。读取时若一条记录的 `source_tags` 同时出现在其服装组件中，程序会把它安全归一化为 `named_outfit`，并把其余组件迁入 `component_tags`；真正的角色档案中角色 identity tag 不会是服装组件，因此保持不变。词库页面保存后会以拆分后的结构持久化。

### 外貌权限与 Identity 合并

外貌修改另有 `operation=omit`：用户明确要求某角色的特征完全不可见时，档案中的该维度不能作为身份保底补回。它先从给 LLM2 的稳定外貌证据中移除，再约束 `Identity`、`Details`、`Nltags`；NAI `-r` 逐角色重写后也再检查一次。例如“爱音上半脸黑着，不画眼睛”应保留遮脸和无可见眼睛的描述，但爱音的 `grey_eyes` 不能并存。此权限仅作用于爱音，不影响同画面祥子的瞳色。旧 planner 对明确眼睛缺席给出 `replace` 时会归一到 `omit`，普通眼神、闭眼或无高光不算特征缺席。

外貌不使用“用户提到任意外貌后整份档案失效”的布尔开关，而是按角色和语义维度裁决。目前稳定维度包括发色、头发长度、发型、瞳色、肤色、胸部尺寸、兽耳、尾巴和角；没有归入互斥维度的标志性特征仍可作为普通稳定特征保留。

每个角色的优先级为：

1. LLM1 输出且可定位到用户原文的该角色 `appearance_changes`；
2. 该目标角色视觉档案的 `appearanceTags`；
3. 第二阶段 LLM 对未建档特征的合理补全。

LLM1 的 `appearance_changes` 不直接注入 tag，而是为该角色输出 `dimension / operation / source_text`。`operation=replace` 只移除该维度的旧档案值，`operation=additive` 保留兼容档案值并允许新增值，`operation=omit` 让该维度的档案值与 writer 猜测都不再进入最终提示词。主机不再扫描具体中文变化关键词。`source_text` 先做规范化精确匹配，轻微改写再走统一的逐句序列相似度与最长公共片段阈值；角色名仍须单独在原文中成立。单独的“扶她/futa/futanari”证据还必须在原文中紧贴对应角色名，不能因为词语出现在请求里就分配给所有人物；它也不能被当作 `chest_size` 修改。主机不再用用户原文正则判断“改蓝眼睛”“双钻头”或“角”等维度，避免把“视角”误判为 horn。共享 `Tags` 中无归属的角色外貌词仍会移除，回到各自的 `Identity` / `Details`。

进入第二阶段前，若 `fixed_characters` 中的旧外貌提示与当前视觉档案冲突，会用目标角色 canonical tag 与最新 `appearanceTags` 重建该角色提示。已有逐角色视觉档案时，LLM2 只收到一份逐角色稳定外貌清单；固定角色辅助信息不会再重复列出同一档案，已确认角色 tag 也不会同时重复出现在 hard-tag 行和角色名单中。第二阶段返回后，Identity 会再次逐维度合并：writer 已正确表达且与档案一致的自然语言保留，只补未表达的稳定维度，并按替换/叠加语义处理开放维度。因此不会在最终 Tags 末尾盲目追加一整份竞争 Identity。

Identity 合并保留句首和句中的 `is` 谓词。例如 `A is a tall mature woman with long blue hair` 会整理为 `A is a tall mature woman and has long blue hair`，不会把句首的 `is` 删除后误补成 `has a tall mature woman`。`with` 后的外貌特征仍经过同一逐维度档案校验，冲突值会被过滤，缺失值仍按权限补齐。

### `WardrobeAuthority` 的五组标签

- `cached_tags`：本次命中角色档案里能找到的历史衣柜组件。
- `explicit_tags`：用户本次服装/套组 anchor 明确提出的候选，以及确定性名词映射。
- `selected_tags`：每个角色实际选中的 default、casual、命名套组、迁移服装或修改后服装。
- `source_grounding_tags`：被选中的 cosplay/outfit source 在数据库中的同源服装证据。它们不会自动全部注入，但可供第二阶段补全来源造型，也不会被误当成穿着者的旧衣柜删除。
- `unbound_grounding_tags`：存在 `explicit_but_unresolved` 时，与未绑定服装/source anchors 同源的可信证据。它们不会成为角色绑定或全局 hard tags，只供第二阶段结合原文判断。
- `stale_cached_tags`：属于旧衣柜，但既没有被本次明确要求、也没有被任何角色计划选中的标签。

只要存在角色级 wardrobe 计划，`stale_cached_tags` 就会从第二阶段上下文、共享 Tags、角色 Details、Nltags、required tags 和最终 prompt 中统一删除。若用户本次明确要求的衣物恰好也存在于旧档案中，它属于 `explicit_tags`，不会被误删。

`Identity`、`Details` 和共享 `Tags` 的职责不同：

- `Identity` 保存角色固有外观。
- `Details` 保存带穿着者的动作、互动、道具和服装描述。
- `Tags` 是没有穿着者信息的共享 tag 区。
- `Nltags` 用于补充 `Identity` / `Details` 尚未表达的关系、动作方向和场景；后处理会删除复制自这两块的句子，不能信任第二阶段模型原始的共享服装叙述。未解析中文只作为 LLM2 上下文，不由主机直接拼入最终块；过滤服装句时也只认实际穿着/裸体断言，不因 `beneath her skirt` 这类定位短语误删动作或性征。

## 用户未说明服装时的策略

配置 key：`unspecified_wardrobe_policy`。

它按角色生效。角色已经有具体衣物、命名套装、服装来源、默认/常服/私服选择时不启用；只有增删、破损、换色等修改但没有说明基础服装时，则使用 default 软参考作为被修改对象。用户显式意图始终优先，配置不能把“穿白色睡衣长裙”改成默认服装，也不能把明确的“默认服装”降级成场景创作。

| 值 | 行为 |
| --- | --- |
| `scene_adaptive` | 推荐默认值。读取该角色 default 作为软参考；普通站立/合影更倾向沿用，涩气或强场景词命中时允许第二阶段适配、替换或补全。 |
| `default_profile` | 未说明时始终把角色视觉档案中的 default 作为软参考，但不强制逐项照搬。 |
| `creative_fallback` | 未说明时始终由第二阶段模型为各角色设计服装。 |

`scene_adaptive_wardrobe_markers` 是可编辑的强场景词列表，采用不区分大小写的子串匹配。内置标记包括泳池边、出浴、睡眠前后、运动/训练结束、比赛、健身、游泳结束和演出结束等。命中表示 default 仅供情境参考，并不等于完全不读取它。`比赛` 会触发这种强情境，但“看比赛、观看比赛、观赛”等旁观语境会被排除；公园、在家、吃饭不会单独触发。

当策略选择 `default_profile`，但目标角色没有可用的 default 服装组件时，程序会把该角色回退到 `creative_fallback`。显式要求“默认服装”时不会偷偷改成 creative；它仍按显式意图处理，方便从档案或查询证据中解决。

多人请求中的显式模式按目标角色所在分句分别解析，而不是生成一个请求级全局模式。逗号、分号以及“而、但是、然后、同时”等转折/并列连接词都可分隔角色局部范围。例如“爱音穿常服而祥子穿默认服装”分别得到 `casual_profile` 与 `default_profile`；“爱音穿私服，祥子穿默认服装”也只让爱音进入 `creative_fallback`。“爱音穿常服和祥子在泳池边玩”只为爱音选择 casual，祥子收到自己的 default 软参考；“爱音和祥子都穿常服”才为两人都选择 casual。default、casual、summer、winter、stage 档案同样按各自角色附近的变体词选择。

调试摘要中的 `wardrobe_source` 会记录本次来源，例如：

- `explicit_default_profile`、`explicit_casual_profile`、`explicit_named_outfit`、`explicit_clothing`、`explicit_creative`；
- `configured_default`、`configured_creative`、`scene_adaptive`；
- `missing_profile_fallback`。
- `explicit_but_unresolved`：用户明确提到服装，但 LLM1 对至少一个角色弃权；默认衣柜被禁止，交给第二阶段结合原文处理。

第一阶段 LLM 对“没有服装信息”的角色只应输出临时 `none`；对“裙子变蓝”“没有上衣”等只有修改、没有基础服装的请求输出 `default_profile + changes`，主机再转成可修改的 default 软参考；对连体泳装、分体泳装、白色卫衣等普通实际衣物输出 `creative_fallback`，此时不加载 default。最终缺省 default/creative 选择仍由上述主机侧规则决定。

## 上下文角色别名映射

配置 key：`danbooru_character_alias_mappings`。

格式：

```text
别名1 | 别名2=canonical_character_tag
```

例如：

```text
复仇者 | revenant=revenant_(elden_ring)
```

它只解决“是谁”，不保存该角色的详细外观或服装。带作品消歧后缀的角色必须在同一请求中命中兼容的 `danbooru_series_alias_mappings`，才会成为权威角色 anchor。

适合保存：

- 中文译名、俗称和罗马字别名；
- 容易被 LLM 拼错的 canonical character tag；
- 需要作品作用域消歧的角色。

不适合保存服装、动作或场景。

## 固定角色辅助信息

配置 key：`fixed_characters`。

格式：

```text
显示名=canonical 角色 tag 与稳定外观信息
```

例如：

```text
狐莉=original_character, 1girl, white_hair, red_eyes, fox_ears, fox_tail
长崎素世=nagasaki_soyo, long_brown_hair, blue_eyes
```

也可以使用聊天命令：

```text
/anm 添加角色 狐莉=original_character, 1girl, white_hair, red_eyes, fox_ears
```

### 匹配方式

只有用户原文包含左侧显示名时才命中。当前是直接的原始子串匹配；出现“不要角色”“无人”等特殊标记时会关闭固定角色命中。

### 不同路径中的真实作用

| 路径 | `fixed_characters` 的作用 |
| --- | --- |
| 普通七字段结构化路径 | 作为本地角色身份辅助信息发给第二阶段模型；用于匹配结构化 roster，但不保证右侧每一个词都被逐项 hard 注入 |
| `/anm 多人` 兼容路径 | 按人物块较强地注入；`1girl`、`1boy`、`solo` 等单人计数词会从人物外观块移除，性别信息仍参与总人数计算 |
| 旧平铺/非结构化回退 | 第一个命中的固定角色整串进入最终 prompt，并清理竞争性身份 tags |
| `/anm 无优化`、原样模式或关闭优化 | 不参与，原始 prompt 直接发送 |

因此旧描述“提到角色名时直接拼接该角色 tags”只对多人兼容路径和旧回退路径完全成立，对当前普通结构化路径并不准确。

### 应保存的内容

- canonical 角色 tag，已知时建议放在第一项；
- 原创角色标识；
- 性别与稳定年龄感；
- 发色、瞳色、种族；
- 耳朵、尾巴、角、翅膀；
- 不随服装变化的标志性身体或身份特征。

### 不应保存的内容

- 默认服装、校服、演出服或私服；
- 本次动作、表情或场景；
- 质量词、画师词和画风词；
- 多人关系和仅在某次请求成立的状态。

把服装放入 `fixed_characters` 会绕过或干扰当前 wardrobe 优先级：普通结构化路径可能把它误当固有身份，多人路径可能直接注入，旧回退路径则会整串全局注入。

## 角色视觉档案

页面位置：`服装词库 → 角色视觉档案`。内部主要保存 `character_outfit` profile。

一条档案包含：

- 档案名称和触发别名；
- `sourceTags`：角色或服装来源 canonical tags；
- `tags`：从帖子样本学习或人工填写的服装组件；
- `appearanceTags`：稳定发色、瞳色、角、耳朵、尾巴等；
- `qualifier`：自由服装名称；兼容 `default / casual / summer / winter / stage`；
- 采样模式、样本数、更新时间等证据。

非默认变体使用独立记录，避免夏季、冬季、演出服和官方常服互相覆盖。

这里的变体必须属于角色本人；不要在“角色视觉档案”中保存可由多人穿着的学校制服或 Danbooru 命名套组。通用套组应进入“服装套组”，并在那里维护 canonical tag、别名、季节变体和套组组件。

角色视觉档案的触发别名同时约束 `target_character` 和 `outfit_source`。匹配采用角色/来源 anchor 内的边界匹配与最长别名优先，因此别名可以位于“SynthV 服装（也就是 kasane teto (sv)）”这类完整来源短语中，而较短的“重音teto”不会盖过“重音tetosv”。命中后会在本地查询前用档案的 `sourceTags` 覆盖 LLM1 的未验证候选；default、casual、stage、summer、winter 仍按 `qualifier` 隔离，不跨变体借用衣柜。对于角色自己的变体，LLM1 给出的穿着者与 `clothing` 会先形成逐角色 profile 意图，再以该角色的 canonical `sourceTags` 和 qualifier 选择兄弟档案，因此 stage 不依赖 `角色名+演出服` 必须在原文中连续出现。

角色衣柜 owner 与变体 qualifier 分开解析：角色别名只负责确定 canonical owner，完整 `clothing` 原文负责确定 `default / casual / summer / winter / stage`。因此“丰川祥子穿着千早爱音的演出服”“丰川祥子穿着千早爱音演出服”“千早爱音穿着千早爱音演出服”和“千早爱音穿着演出服”都会选择 `(chihaya_anon, stage)`；前两种再把该档案绑定给丰川祥子，后两种绑定给千早爱音。不得先按 qualifier 过滤角色别名，也不得只用 `clothing_source=千早爱音` 查询而丢弃 clothing 中的“演出服”。

已有档案的编辑器可见 `tags` 和 `appearanceTags` 是当前请求的权威组件。新鲜档案不重复采样；证据过期时可以刷新帖子统计，但刷新结果不能绕过或临时替换人工档案。读取时使用最长非重叠别名，写入防重则只拦截完全相同的触发别名，因此“黑魔导”和“黑魔导女孩”仍可分别建档。若同一精确别名已经属于不同 `sourceTags`，会拒绝自动新建；已有别名冲突只有在来源变体后缀等原文证据足够明确时才自动消歧，否则保留为歧义而不继续扩散。

自动学习的服装组件只受帖子支持度、服装类别与冲突消解规则筛选；通过这些证据规则的 tags 不再受固定数量上限截断。

### 使用方式

- `default_profile` 使用角色默认视觉档案。
- `default_reference` 是主机内部状态：用户没有给该角色实际服装基础，或只给了修改要求时，把 default 组件作为第二阶段的可修改参考；它不是 LLM1 可输出的 wardrobe kind。
- `casual_profile` 使用官方 casual 档案。
- `named_outfit` 使用命名套组 tag，并可附带该套组的帖子组件档案。
- `outfit_source` 使用来源角色或人格的可迁移服装档案。
- `outfit_source` 同时覆盖 cosplay 和普通借衣；只有原文明确表达穿着者对来源角色的 cosplay 意图、且来源已确认成 canonical 角色 tag 时，最终 Tags 才补一条来源角色的 `_(cosplay)` tag。仅借衣、否定 cosplay、未确认来源及被重新归为通用命名套组的请求不补。
- `creative_fallback` 不注入默认/常服档案，只保留稳定外观，让第二阶段模型设计本次衣服。

本地衣柜会复用统一的构图分类裁剪不可见组件，而不是只判断 `cowboy shot`。当前分类覆盖头部/脸部特写、上半身、cowboy shot、肚脐、下半身、腿/大腿/臀部、足部、手部以及头部出框，并统一解释“只拍/只画到腰、膝等部位以上”的最低可见边界；每类只删除确定在画外的衣物槽位。用户原文的构图在进入第二阶段前裁剪，画外组件只保留在内部诊断数据中，不把具体 tag 再提示给第二阶段；第二阶段最终 Tags 自己选择的构图还会触发一次后处理裁剪并重建 `WardrobeAuthority`。后置 prose 权限也会删除带颜色、材质或样式修饰的画外衣物短语，例如 `green pleated skirt`。这是减少不可见档案噪声，不是更换服装；用户补丁明确新增的状态仍受保护。中文“下半身没穿”“上半身没有衣服”等服装修改不会被误判为镜头，只有限制画面范围的相机/可见性表达才触发中文裁剪。

当前语义中，“官方常服/常服/casual outfit”选择 `casual_profile`；“私服/居家私服/居家服/休闲穿搭”选择 `creative_fallback`，两者不是同义词。

### 最终注入

- `appearanceTags` 按维度与用户显式外貌修改、第二阶段 Identity 合并；未开放维度会删除 LLM 的冲突描述后使用档案值。
- 有效服装 tags 在应用用户增删、换色等补丁后，只作为对应角色的 LLM2 证据和后置冲突边界；本地主机不再把整套组件追加到 `Details`。
- 当前后处理不会再从 `Details` 重建服装 `Nltags`；重复的服装或外貌句会被去除。
- 无论单人还是多人，角色视觉档案的服装组件都不会自动进入共享 tag 区；最终可见服装只取 LLM2 在用户原文和逐角色证据下写出的内容，再经过删除、stale 与跨角色过滤。
- 所有可见角色都是 creative 时，第二阶段模型可以在共享 `Tags` 中输出真正适用于全员的普通服装 tags；各角色不同的衣物仍只能写在各自 `Details`。
- 多种状态混合或多人服装不同时，共享 `Tags` 只保留真正适用于全员的安全项；角色特有服装由第二阶段写进带名字的 `Details`。这是角色所有权过滤，不是以数据库组件构造服装白名单。
- creative 共享 Tags 仍会删除校服/制服和裸露状态，避免模型凭空发明命名校服或绕过服装权限。

## 服装套组与兼容配置入口

页面位置：`服装词库 → 服装套组`。

配置 key：`danbooru_named_outfit_mappings`。普通配置页中的“服装套组映射（兼容配置入口）”和页面里的服装套组是同一系统，不是两套功能。

格式：

```text
别名1 | 别名2 | 别名3=canonical_outfit_tag
```

例如：

```text
月之森校服 | 月之森制服 | tsukinomori school uniform=tsukinomori_school_uniform
```

命中后程序创建 `role=outfit` 的语义 anchor。语义规划通过 `named_outfit + anchor_id` 把完整套组绑定给具体目标角色。若存在该套组的视觉档案，会同时使用验证过的组件；没有组件档案时，仅使用完整 canonical 套组 tag，不让第二阶段模型自行猜测衬衫、裙子、鞋袜等组成。

服装套组记录现在自行保存验证过的 `component_tags`，不再借用或生成一条同名 `character_outfit` 来承载组件。因此同一套组可以在不同请求中绑定给任意角色，也不会被某个角色的 default/stage 衣柜权限误判为陈旧缓存。

### 回归验证

普通回归使用 `tests/test_danbooru_semantic.py` 和 `tests/test_prompt_strategy.py`，覆盖旧通用套组缓存迁移、词库编辑往返、任意穿着者绑定，以及完整命名套组直接进入 LLM2 而不重复联网补全。真实 provider 验证位于 `tests/live/test_deepseek_prompt_e2e.py`，重点场景包括：

- 高松灯穿羽丘冬季校服：LLM2 必须收到通用套组 canonical tag 与冬季组件，且不得混入月之森制服。
- 对任何“角色穿着／换上……衣物”的直接逐角色表达，LLM1 漏报时都不再恢复该角色的默认衣柜。若省略的衣物是本地已确认的命名套组，则按穿着者绑定套组；其他衣物保留原文交给 LLM2 解释，并标记为服装尚未解析。穿着动词和套组名称之间可以有修饰语；用户对套组的修改优先于原版组件。仅同句提到角色而没有直接穿着关系，不会把别人的衣服分给该角色。
- 千早爱音穿角色自己的演出服、高松灯穿通用羽丘冬季校服：两类衣柜必须分别解析和逐角色绑定。
- 两名角色共穿羽丘夏季校服：同一通用套组证据必须分别提供给两个穿着者。

live 用例默认跳过，只有显式设置 `ANIMA_RUN_LIVE_LLM_E2E=1` 才会调用当前 AstrBot 配置的 provider。断言以主机交给 LLM2 的结构化衣柜证据为准；最终自然语言允许模型合并同义表述，但 canonical 套组和逐角色归属仍必须保留。

### 为什么配置默认只有月之森校服

`月之森校服=tsukinomori_school_uniform` 是该功能加入时留下的一条历史种子，不是完整服装列表，也不是程序唯一支持的套组。

套组有两类来源：

- 手动套组保存在 `danbooru_named_outfit_mappings`，会显示在普通配置页；
- 自动学习套组保存在视觉档案缓存，标记为 `origin=learned`，通常只在服装词库页面显示。

因此普通配置页可能只有一个月之森条目，而服装词库页面有更多自动学习套组。该默认项可以删除；删除只会移除这条手动种子，已有自动学习记录仍可能继续命中。

### 安全限制

- 自动学习不会把泛化的 `school_uniform` 或 `uniform` 保存成某个专名校服。
- 手动配置优先于冲突的自动学习别名。
- 不同套组实体可以指向同一个 canonical tag；匹配时仍保留各自别名和变体 anchor，最终 hard tag 会去重。
- 正常结构化路径可以绑定穿着者；如果角色计划构建失败，才可能退化为无归属的全局套组 tag。

## 名词翻译

页面位置：`服装词库 → 名词翻译`。

配置 key：`danbooru_term_mappings`。

格式：

```text
中文名词或触发词=canonical_tag
```

例如：

```text
舞会面具=masquerade_mask
芭蕾舞裙=tutu
白丝袜=white_pantyhose
```

从提交 `05577f7` 开始，名词翻译只有这一处配置/页面数据源，不再另有代码内置映射。

### 当前行为

程序把用户原文转小写后执行简单子串命中。显式否定窗口（如“不要/不戴/移除/without/no/not”）中的命中会被忽略；同一个词在别处还有非否定命中时仍会加入。有效结果直接进入 `confirmed_tags`，不经过第二阶段模型，也不再联网验证，然后作为全局 hard tag 和服装清理白名单的一部分。

它没有保存：

- 穿着者；
- 语义角色；
- 服装槽位；
- 可供后续阶段使用的结构化否定状态（当前只在命中时过滤常见显式否定）；
- 作品或角色作用域。

所以它适合道具、场景、材质、普通视觉概念和单人请求中的明确衣物；不适合多人场景里只属于其中一个角色的服装或配饰。

例如：

```text
爱音穿芭蕾舞裙，祥子穿西装
```

`tutu` 仍是全局 tag，理论上可能污染祥子。需要角色归属的完整套装应使用服装套组；普通衣物若需要稳定的多人归属，则还需要未来的角色级名词绑定数据结构。

## 服装优先级

当前设计目标为：

1. 用户为该角色明确指定的普通衣物、命名套组、服装来源或 default/casual/season/stage 衣柜，以及其增删、换色和保留操作；
2. 只有修改、没有说明基础服装时：以该角色 default 软参考为基础应用修改；
3. 完全没有该角色服装证据时：由 `unspecified_wardrobe_policy` 决定提供 default 软参考还是完全交给第二阶段创作；
4. 第二阶段在上述权限内根据场景补全未指定细节。

角色稳定外观不参与上述衣柜竞争，它始终按角色独立绑定；只有用户明确修改发色、瞳色等外观时才让本次要求覆盖档案。

需要注意，名词翻译是全局 hard tag 快捷入口，并不天然服从角色级优先级；`fixed_characters` 在多人和旧回退路径中也可能较强地注入。因此不要用这两个入口长期保存角色专属服装。

## 典型例子

### 两名角色共享新服装

```text
百合婚礼、双女主、千早爱音、丰川祥子、白色婚纱、头纱、长手套
```

第一阶段应为爱音和祥子分别建立 `creative_fallback` 计划，并把婚纱服装 anchor 的共享范围展开到两人。两人的稳定外貌继续来自视觉档案；两套 default 校服进入 `stale_cached_tags`。即使第二阶段返回 `haneoka_school_uniform`、`grey_jacket` 或 `green_skirt`，这些旧档案组件也会从所有输出通道删除。

### 一人新服装，一人明确默认衣柜

```text
爱音穿白色婚纱，祥子穿默认服装，在教堂合影
```

爱音使用 `creative_fallback` 并保留婚纱要求；祥子使用 `default_profile`。祥子选中的 default 组件属于 `selected_tags`，不会被当作失效缓存；爱音的旧 default 组件不应进入她的角色 Details。两人不同的服装主要通过带角色名的 `Details` 表达，不依靠无归属的共享 Tags，也不再复制到 Nltags。

这里的“默认服装”由用户明确写出，因此祥子的 `default_profile` 是较严格的已选基础。若请求仅为“爱音穿白色婚纱，祥子在旁边合影”，爱音仍使用婚纱且不读取自己的 default；祥子没有实际服装基础，会收到自己的 `default_reference`。普通合影中第二阶段应倾向祥子的默认衣柜，但仍可根据完整画面协调细节。

若改成“爱音穿白色婚纱，祥子在泳池边玩”，祥子的 default 仍会作为参考提供，但强场景允许第二阶段据此重新设计更合适的衣服。若改成“爱音穿连体式泳装，祥子穿分体式泳装”，两人都已有明确的普通衣物基础，两份 default 档案都不读取。

### 完全没有服装信息

```text
千早爱音和丰川祥子在公园合影
```

第一阶段对两人输出临时 `none`。主机随后按角色让 `unspecified_wardrobe_policy` 选择 default 软参考或 creative。若选择 default，各角色只读取自己的档案；若某人的档案缺失，只有该角色回退为 `creative_fallback`。

### 只修改衣服但不指定基础

```text
千早爱音和丰川祥子站在一起，但下半身没穿
```

第一阶段把修改展开到两人，并以各自 default 软参考为修改基线；“下半身没穿”是强制最终状态。若加入“在泳池边”，第二阶段仍会看到默认参考与这条强制修改，但可结合泳池情境自行决定其余服装。若写成“千早爱音穿羽丘夏季校服但没穿短裙”，基础已经明确改为羽丘夏季校服，不再调用爱音 default。

### 不同命名套组

```text
爱音穿羽丘冬季校服，祥子穿 Oblivionis 演出服
```

第一阶段分别输出 `named_outfit` / `outfit_source` 及对应 anchor。数据库只为每个 anchor 提供候选组件，`WardrobeAuthority` 按穿着者选择；第二阶段不得把 Oblivionis 组件写给爱音，也不得把羽丘校服扩散给祥子。

## 推荐配置分工

| 需求 | 推荐入口 |
| --- | --- |
| 中文角色名对应 Danbooru 角色 | 上下文角色别名映射 |
| 原创/冷门角色的稳定身份 | 固定角色辅助信息 |
| 角色默认服装、官方常服和稳定外观 | 角色视觉档案 |
| 有专名的完整校服、演出服或套装 | 服装套组 |
| 无需绑定人物的道具、场景、材质或普通 hard tag | 名词翻译 |

## 维护注意事项

- 服装词库页面保存使用 revision 乐观锁，避免覆盖其他会话刚写入的档案。
- 页面保存后运行时配置与缓存立即更新；安装或更新页面代码后才需要重载插件。
- `fixed_characters`、名词翻译和中文套组别名目前均包含不同程度的子串匹配，应避免过短或容易出现在普通句子中的触发词。
- 修改角色计划、服装清理器、结构化字段职责或最终 prompt 拼接顺序时，应同时更新本文。


### 带标点的括号角色别名

主机在验证 LLM1 的 `name / aliases` 确实构成原文相邻括号对后，保留合法 Danbooru 名称中的冒号、感叹号和消歧括号，例如 `S:P little knight` 转为 `s:p_little_knight`。英文候选绑定回该中文角色已有的 anchor ID，角色服装计划和学习结果使用同一 ID；不会把括号英文当作额外可见角色。配置中的权威映射仍优先，外貌等非角色括号翻译仍不进入角色学习。


## 自由命名衣橱与完整造型标签（2026-09-12）

角色衣橱不再限定为五种模板。页面的“服装名称 / 变体”可以填写任意名称，例如 `Master of Melodia`、生日礼服或月夜巡演；`default / casual / summer / winter / stage` 继续兼容，只是快捷建议。每套服装独立保存，按角色归属与本次明确服装名称/别名选择。不同角色可拥有同名服装；同一角色有多个同名候选时不任意挑选。

- `ownerTags`（存储为 `owner_tags`）：所属角色；旧记录未提供时兼容原来的来源角色。
- `sourceTags`：学习来源的精确 canonical tag，可以与所属角色不同。
- `qualifier`：自由服装名称，按名称隔离记录；`tags` 是可编辑服装组件。

第一阶段依旧只输出角色、服装原文及来源，不负责猜 tag。主机保留逐角色的 clothing anchor 关联，再用“角色 + 名称/别名”选择具体衣橱记录，并用独立 anchor 绑定每个穿着者。选中的本地组件在查询不可用时仍可交给第二阶段；没有独立来源、只有自定义名字的服装不能靠基础角色帖子自动猜出组件，需要人工维护证据。手工清空的组件不会借学习默认服装自动填回。

完整 `角色名 (造型名)` 不再被基础角色的较短缓存别名覆盖。本地词典缺失时，对用户明确写出的完整服装来源作受限在线精确校验；名称必须完全一致、未废弃且存在帖子。普通分类的造型 tag 只作服装采样来源，不作为可见角色或作品身份。对于直接点名的完整造型，只有查询确认属于普通分类、且基础角色已经在本地确认时，才拆成“基础角色 + 服装来源”；角色分类的 persona/作品消歧后缀不因此改成服装。

例如重载后可使用：

```text
/anm 丰川祥子穿着togawa sakiko (master of melodia)的衣服，站立
```

该来源在当前只读实测中通过在线精确校验，并得到 56 个服装聚类样本，保存为独立的 `master of melodia` 变体。普通分类来源不学习角色外貌，也不把括号后缀当作品名。已有基础角色时会记录其 owner；不能确认 owner 时留待人工明确。它仍是帖子标签统计，不代表逐图视觉校验或官方设定认证。采样不足仍不建档；网络失败不能悄悄回退基础角色校服。

学习后可以在衣橱页面调整名称、所属角色和触发别名。未维护对应中文或简称别名时，只写 `master of melodia` 仍可能无法解析；首次建议使用完整来源。页面与代码更新需重载插件，之后保存衣橱立即生效。
