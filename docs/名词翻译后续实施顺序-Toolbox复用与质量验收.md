## 2. 总顺序与优先级

**先复用现成材料建立候选 → 修复已证实的匹配边界 → 改善页面加载 → 加入释义与审查界面 → 验收小批次 → 必要时续用 DeepSeek → 授权后应用与真实验证。**

| 顺序 | 工作 | 主要目的 | 完成后才能做什么 |
| --- | --- | --- | --- |
| 0 | 重新核对基线、现有代码和断点 | 避免覆盖用户与其他对话工作 | 开始增量实施 |
| 1 | 复用 Toolbox 别名、分类和释义，补充离线候选 | 减少重新翻译；看清词义与检索歧义 | 确定需要修机制和需要人工判断的项 |
| 2 | 修复可保守处理的匹配问题，记录不能可靠处理的情况 | 减少否定、短词漏入和非视觉误导 | 用新机制评估候选的实际可用性 |
| 3 | 测量并改善词库页面加载 | 让后续审核可顺畅进行 | 扩展审核界面 |
| 4 | 在维护/审核界面加入 tag 说明、候选搜索和正反例 | 降低人工辨析成本 | 审查原库疑点及小批次候选 |
| 5 | 人工确认必要疑点，并做新的独立验收 | 确认小批次值得应用 | 形成可审查的发布清单，或明确暂缓 |
| 6 | 对剩余真实缺口使用 DeepSeek，沿原断点续译/复核 | 把付费调用集中在现有材料不足之处 | 新产物回到阶段 4–5，不直接导入 |
| 7 | 授权范围内发布小批次，另行开展真实模型/生图验证 | 保存、同步、恢复并验证实际收益 | 根据真实缺口决定下一批 |

阶段 3 的页面测量不依赖阶段 2，可提前做；页面提速作为独立改动验收，不与 resolver 重构混成一次大改。阶段 4 的界面扩展在加载问题定位之后实施。人工词义审查可以先用文件进行，不必等待界面完成。

每阶段交付可复核的独立结果。发现语义问题时先保留原文、暂缓候选，不以扩量或更长模型循环绕过失败。

## 4. 阶段 1：复用 Toolbox，避免从头翻译

### 4.1 可以复用什么

| 材料 | 用途 | 边界 |
| --- | --- | --- |
| `tags_index_v2.json` 的 general tag 与中文别名 | 找现成自然表达与不同译法 | tag 和别名都需核对，不直接写入运行映射 |
| `tag_gloss.json` 的释义、误读提醒与易混辨析 | 辅助理解和审核 | 是来源材料，不自动成为权威定义 |
| `tag_browse.json` 的分类 | 缩小候选搜索范围 | 分类帮助查找，不证明本后端分类或标签有效性 |
| 已有本地 Anima/Danbooru 目录 | 核对 canonical 名称及本地分类 | 缺失只表示目录覆盖不足，不等于 NAI 不支持 |
| 原有 1427 行及模型翻译/复核断点 | 避免重复处理并保留人工决定 | 不覆盖原值，不把“已有”当作语义正确金标准 |

不将外部角色特征、服装组件或画师数据混入这次通用名词候选，不以外部分类建立可见身份或衣柜权限。复用数据/代码时继续保留 `third_party/llm_nai_toolbox/` 的来源和许可材料，并记录来源版本、字段、文件散列与复用范围。

### 4.2 区分自主翻译词库、Toolbox 原始库与此前导入结果

当前本地 Toolbox 文件与历史导入清单核对结果如下：

| 表达 | Toolbox 原始库/历史导入记录与现有词库对照 | 实际含义 |
| --- | --- | --- |
| 拥抱 | Toolbox 含该词；自主翻译词库也已有 `hug`，两者来源独立 | 内容重合，无需重复新增 |
| 抱抱 | Toolbox 有该词，历史导入候选指向 `carry_me` 与 `hug`，被歧义过滤跳过 | Toolbox 并非没有自然说法；不能直接强选 `hug` |
| 抱拥 | 历史新增为 `hug` | 格式单值不代表比“抱抱”更自然 |
| 摸头 | 指向 `headpat` 与 `hand_on_another's_head`，被跳过 | 需区别动作与静态手部位置，不能仅靠去重裁定 |
| 白裙 | 指向 `white_dress` 与 `white_skirt` | 衣物形制未确定，允许不命中 |
| 俯视 | 指向 `from_above` 与 `looking_down` | 相机方向与人物视线不同，需语义上下文 |

因此，不因部分坏别名否定整个 Toolbox 库，也不以“单值、热门、zhFull 字段”作为自动批准依据。Toolbox 的不同字段都是候选证据；自主翻译词库的质量另按实际请求核对。

### 4.3 候选如何整理

先针对首轮实际缺口、原库待复核项以及用户反复使用的概念检索已有材料，不从整个英文热度榜重新翻译。可以建立本地维护索引来检索整个来源库，但**维护索引不等于第二个自动参与生图的运行词库**。

候选按概念聚合：canonical、中文释义、多个自然别名、来源字段、容易混淆的 tag、正例、邻近反例、原值冲突、后端覆盖与审查状态。自然别名不限机械数量；整段请求、随意添加主语、否定句及语气词穷举不作为补洞方式。

采用以下状态：

- 原有同值：记录后跳过新增。
- 有等价依据、尚待匹配验收：进入小批次候选。
- 不等价或附加/丢失条件：拒绝，并保存原因。
- 多义或依赖上下文：暂缓，原文留给现有 LLM 阶段。
- 目录未覆盖或解释证据不足：待复核，不编造后端能力。

当前候选的自然变体没有测得增益，不等于词义错误；不足时保留待验证，不按条目数量凑批次。

**交付：** 新批次候选记录、来源证据、冲突/歧义清单，以及“已复用、仍需判断、仍需翻译”的差异表。不应用配置。

## 5. 阶段 2：修匹配边界，保留弃权能力

先处理已被正反例证实的问题：

1. 否定词与衣物之间有“想、打算、穿、戴”等文字时，现有紧贴否定窗口不能覆盖。
2. 长别名被否定后，内部短词仍可能命中，例如“不戴半指手套”里的“手套”。
3. 引述、比喻、愿望或其他非实际画面条件，不能仅因包含词条就当作正向视觉参考。

从作用域与命中位置定位一般规则，不为球鞋、公园或某句原文写特判。不承诺用正则解决全部中文语义；只有能用请求证据保守确定的范围才做过滤，无法可靠判断的词条继续暂缓。引用中确有用户要求显示的文字也应区别于实际场景对象，不能“一切引号都删除”。

必须保持：最长重叠优先、其他独立位置的短词仍可命中、同词另有正向出现时保留、配置更新缓存失效、停用开关有效。一个人否定某衣物不能删除另一个人的正向要求；匹配也不据此猜穿着者或恢复默认衣柜。

不要同时引入自动模糊匹配、编辑距离猜词、去掉全部语气词或多候选生图协议。名词继续只是参考，不变 hard tag，不补回模型未采用的 tag，不因缺词重试或阻断提交。

**验收：** 使用首轮失败作为开发回归，补充不同对象、不同语序、多人、独立正向位置等反例；同时报告误命中减少和误删正向参考。无法安全解决的情况明确保留。改动 resolver 后更新相关流程文档。

## 6. 阶段 3：先测量，再改善页面加载

已观察到的代码事实：页面初始化等待 bridge 就绪后读取完整 wardrobe；独立批量翻译面板也在初始化时请求进度。当前列表已经分页渲染，不能把“再加分页”当成已定位的解决办法。尚未测量真实等待各环节的耗时，不声称 CSV 扫描、网络或渲染已经被确认为根因。

依次测量：页面 bridge 就绪、请求等待、后端快照/进度计算、传输、数据复制和首屏渲染。记录冷开与再次打开的结果，确认显示“等待”究竟发生在哪一段。

根据测量选择必要改动：优先显示当前分类；批量面板展开时再加载重型进度；后台作业状态与完整候选/审核表分开读取；可缓存的目录和派生统计按来源/断点/配置版本失效。将耗时的同步本地处理移出阻塞请求路径时，必须保留状态一致性。

### 保存边界比首屏速度更重要

- 不以缓存假装实时同步，不用迟到响应覆盖未保存编辑。
- 切分类、翻页和刷新保留编辑，不只保存当前页。
- 若分区读取数据，保存端必须使用可靠的分区更新，或先取得完整最新快照再合并；不能把未加载分类当空数组提交并清空用户数据。
- 保留 revision 冲突检查、人工数据优先和明确的加载失败状态。
- 长模型作业不能因面板隐藏而丢失；显示时重新取状态，无需持续读取全量审核表。

**验收：** 同一实际数据规模下报告首屏与刷新耗时；检查跨页编辑、未加载分类保留、并发 revision、慢响应、错误重试和批量作业恢复。页面提速不宣称词条质量改善。

## 7. 阶段 4：把释义和候选搜索用于审核

审核界面应让人能同时看到：canonical、中文释义、来源与覆盖、自然别名、容易混淆的概念、正例/反例、当前已有值、建议变更和暂缓原因。原映射列表与外部候选分开，不能因浏览候选自动保存。

提供“保留原值、接受候选、修改别名、暂缓/拒绝”操作与可追踪决定。用户使用语境可以作为依据，例如“事后”；不能机械套用所有日常语言含义。原库 54 项先做复核，不批量删除。

模糊搜索首先用于维护界面：帮助在别名、释义和分类中找到候选，显示为何相关。搜索相似度不等于语义置信度，结果不自动加入名词映射，不凭分数赋予角色、衣柜或 hard-tag 权限。

释义、辨析和反例先留在维护文件/界面里。运行配置继续使用已验收的 `alias=tag`；不默认把整个释义库或每条反例塞入 LLM 上下文。以后若验证少量按需释义确有收益，再独立设计对现有 LLM2 的有限参考输入，不默认增加调用或移植十轮工具循环。

**交付：** 可审查的候选界面或等价维护流程、人工决定记录、仍有争议的清单。界面许可用户审核，不能把本次规划当成批准改写原词库。

## 8. 阶段 5：用新验收集形成合格小批次

原 36 条验收样本在结果揭晓后可继续作为回归，但已不能作为下一次选词后的独立验收证据。为新批次提前准备并冻结新的验收集；开发时不按验收结果不断添词。失败后修订的批次应另设新的独立验证，保留失败历史。

对同一集合比较当前原库与“原库 + 小批次候选”，分别报告：新增正确参考、丢失的旧参考、净变化、新增错误、减少的原库错误、仍缺失、冲突跳过和允许弃权。区分父概念参考与细分概念覆盖，不把标签存在、任意字符串命中或单项新增数当成整条请求正确。

首批发布门槛：有可说明的等价依据；新验收集中候选新增明确错误为 0；有实际新增正确参考；没有不可接受的正向误删、数据覆盖或性能退化。0 错误仅针对有限样本，不保证所有中文。达不到时暂缓或缩小批次，不靠规模掩盖失败。

不要求用户逐项从头审核整个库。程序完成格式、重复、冲突、覆盖与正反例检查；人工集中确认原库疑点、准备应用的别名，以及模型/释义不能可靠裁定的争议。

**交付：** 新冻结评估、逐样本差异、审查决定、可发布的小批次清单，或明确说明未达标的结果。候选是否应用必须单独记录。

## 9. 阶段 6：必要时继续 DeepSeek，保留原进度

只有来源材料不足、已有解释仍有争议或确有自然中文缺口时，才把相关小批次交给 DeepSeek。能复用的别名和释义无需重译。

可以提交 canonical、已有别名、释义、易混 tag 与使用约束，让模型检查等价性、修订生硬表达并说明限定条件；证据不足允许空别名或暂缓。模型结论仍是候选，回到阶段 4–5 审查与评估。

保留原翻译和复核断点、已处理 tag 与人工修改，不重跑已完成全库。先核对实际进度及状态，再沿断点续用；修订某个已处理项应另记修订版本，不覆盖原证据。

当前批量初译协议最多 2 个别名，仅输出 tag/aliases，另有独立复核请求。若此阶段确需加入释义依据、反例或允许合理数量的别名，再修改任务书、解析器、状态存储与测试；不能只改提示词、让旧解析器拒绝新输出，也不能覆盖现有未跟踪实现。协议变更须兼容历史断点。

优先执行少量试批，报告调用次数、费用信息可获得性、拒绝/暂缓、实际增益。独立复核请求不意味着模型判断必然正确；不以自动复核替代语义验收。收费调用依当时明确授权，本规划不启动模型。

## 10. 阶段 7：应用与真实效果验证

只有用户授权应用且批次已达门槛时，才通过已有安全持久化入口写入运行词库。不重新使用 general 全量导入路径。应用前核对配置是否变化；人工原值优先；保存词库快照和实际新增清单；重复合并幂等；恢复只移除仍等于该批次值的新增项，保留用户后改内容和其他配置。不得覆盖 `toolbox_import/applied.json`。
