# 从用户中文描述到 ComfyUI 英文正向提示词

> 本文按当前插件代码整理，说明一次普通“文本生图”请求中，中文怎样变成最终交给 ComfyUI 的英文正向提示词。它面向不熟悉代码的维护者：前四节讲大方向，后半部分适合排查和改配置。
>
> 范围：`/anm generate`（及“生图 / 画图”别名）和 `/anm multi_person` 的文本生图链路。改图、反推咒语、验图重试有共用部分，但不是本文主线。

## 结论先行

插件**没有一个把中文逐字翻成英文的独立翻译器**。正常优化路径分为两个 LLM 阶段：第一次 LLM 是“语义规划器”，负责识别可见角色、判断“谁穿什么”，并把“两人都穿婚纱”这类共享范围展开到每个角色；第二次 LLM 是“提示词写作者”，在本地服装权限已经确定后输出英文七段结构。角色数据库提供身份、稳定外观和候选衣柜，`WardrobeAuthority` 再从用户要求、规划结果和缓存中裁定本次允许或必须删除的服装标签。

```text
中文请求
  → 第一次 LLM 判断角色与逐角色服装归属
  → 角色档案 / 可选 Danbooru 查询提供证据与候选
  → WardrobeAuthority 选中本次服装并标记陈旧衣柜
  → 第二次 LLM 输出英文七段结构
  → 同一服装权限过滤并拼入质量/画师/角色预设
  → 英文正向提示词（--prompt）
  → ComfyUI 正向文本编码节点
  → KSampler 出图
```

因此，ComfyUI 收到的是英文正向提示词；**正常优化路径下不会把中文原句直接交给 ComfyUI**。例外是关闭优化或使用 raw（原样）模式，见“绕过与失败分支”。

## 三种容易混淆的“提示词”

| 名称 | 谁使用 | 内容 | 是否直接给 ComfyUI |
| --- | --- | --- | --- |
| 用户原始提示词 | 用户、插件 | 中文描述，例如“画一个雨夜撑伞的粉发女孩” | 否（正常路径） |
| LLM 任务书 | 插件调用 LLM 时 | 中文规则 + 用户原文 + 检索/角色等上下文 | 否 |
| 最终正向提示词 | ComfyUI | 英文 tag、英文描述、质量/画师/角色预设、`Nltags` | 是，作为 `--prompt` |
| 负向提示词 | ComfyUI | 例如低质量、低分数等要避免的内容 | 是，但不经过本流程 |

Danbooru tag 可粗略理解为模型常见的英文画面关键词，如 `1girl`、`pink hair`、`holding umbrella`。最终内容不必全是严格 tag：`Identity`、`Details`、`Nltags` 可以保留简短英文自然语言，以补足关系和细节。

## 1. 命令进入生成任务

命令入口在 `main.py`，动作分发在 `command_actions.py`。普通生图调用 `main.py` 的 `_generate()`，再进入 `GenerationTaskRunner.generate_payload()`（`generation_task.py`）。在真正优化前会做：

1. 检查权限、配额，以及 ComfyUI 是否可连通。
2. 按第一个 `#` 拆文本：前面是交给优化器理解的主描述，后面是用户强制保留的手工尾缀。
3. 若用户请求参考图，或引用一段旧咒语，先将参考上下文追加到主描述。
4. 调用 `PromptPipeline.build()` 得到最终正向提示词；再将 `#` 尾缀插回、且放在 `Nltags:` 前。

例如：

```text
用户输入：画一个粉发女孩在雨夜撑伞 # cinematic lighting, depth of field

交给优化器的主描述：画一个粉发女孩在雨夜撑伞
最后强制插回的尾缀：cinematic lighting, depth of field
```

`#` 后内容不会被 LLM 翻译、重写或标签清洗。它适合已会写英文 tag 的用户；拼错、写中文或写冲突 tag 时，插件通常不会替你修复。

## 2. `PromptPipeline` 的本地预处理

核心入口是 `prompt_pipeline.py` 的 `PromptPipeline.build()`。它先整理输入，再决定需要哪些辅助信息。

### 2.1 清洗与预设

- 删除旧式 `--自由发挥`、`--创意拓展` 等标志，整理重复逗号和空白。
- 识别 `-s1`、`-s2` 等画师组选择器；选择器从用户描述中移走，改为选择配置里的画师预设。
- 通过 `apply_config_preset()` 读取配置预设；预设可同时改变质量词、画师词、工作流等默认项。

### 2.2 两种“不会翻译”的直通情况

| 情况 | 触发方式 | 结果 |
| --- | --- | --- |
| 关闭提示词优化 | `prompt_optimize_enabled=false` | 清洗后的用户文本直接返回，可能仍是中文 |
| raw / 原样模式 | `原样`、`直接画`、`不优化` 等前缀（`strip_raw_prefix()` 识别） | 去掉前缀后直接返回，适合自己写英文 tag |

这两条分支不调用 LLM，也不拼默认质量词/角色词。若 ComfyUI 文本编码器不擅长中文，出图质量可能下降。

### 2.3 从中文中识别的辅助意图

未绕过时，插件会准备以下上下文：

- **固定角色**：`fixed_characters` 中命中的角色名称及其保存的标签/外观提示。
- **角色视觉档案**：解析器提供的角色核心 tag、外观档案、默认服装证据。
- **关键词规则**：配置中为某些中文词设置的硬性提示词要求。
- **感性模式**：命中相关词时，提醒 LLM 不要把用户明确要求的透明材质、表情、姿势等弱化成普通日常画面。
- **服装迁移**：如“让 A 穿 B 的衣服”；识别来源、目标和明确改动，避免把来源角色本人错误搬进图里。
- **背景意图原文**：保留追加参考上下文前的用户文字，后面以它为准判断用户是否真的要求背景。

## 3. 第一次 LLM 语义规划与可选 Danbooru 验证

这一步不直接生成最终咒语，而是给后续英文输出增加“有依据的角色/服装/作品标签”。其失败通常不阻断普通生图。

### 3.1 用户要求联网或深度思考

`prompt_research.py` 会检查中文关键词：

- 出现“联网、搜索、搜一下、查一下、官方图、设定图、资料”等，且配置允许、Tavily Key 可用时，执行网络搜索；搜索摘要会给提示词 LLM。
- 出现“深度思考、认真想、仔细想、严格还原、高度还原、不要跑偏、核心特征”等，且配置允许时，调用 LLM 时开启深度思考。

联网结果只用于理解角色、服装、动作和视觉符号；模板明确禁止把网页标题、网址或出处写进最终 tags。

### 3.2 先规划角色与服装，再按条件验证标签

只要正常优化路径具备语义规划接口，第一次 LLM 就会运行；它不再以本地 Danbooru 查询是否可用为前提。它从中文中识别目标角色、作品、服装和道具，并输出逐角色 `character_plans`。遇到“双方、两人、都、双女主、both、all”等范围词时，必须把同一服装要求展开到所有目标角色。

`outfit_source` 和 `named_outfit` 关系必须在 `wardrobe.anchor_id` 中引用对应 anchor。若 LLM1 已经输出逐角色计划、但引用缺失、悬空或角色类型错误，程序会把具体校验错误和原回复交回同一规划器修复一次；程序本身不猜引用。若 LLM1 根本没有提出关系，则仍视为语义弃权并进入 `explicit_but_unresolved`，不会为了凑结构而强制重试。

`danbooru_resolver.py` 随后提供角色身份、稳定外观和缓存的候选衣柜；本地查询可用时再验证候选 tag。查询不可用只代表跳过标签验证，**不代表跳过第一次 LLM 的服装归属判断**。

服装修改使用语义操作而不是中文句式匹配：`remove` 删除衣物，`damage` 保留衣物但改变为破损状态，另有改色、增加和仅保留指定槽位。角色/来源数据库只描述未修改的证据；用户修改会在其上形成请求级最终状态。被删除的来源 tag 会从所有允许集合扣除，破损和缺失状态则按穿着者写回 Details/Nltags。外貌采用“角色 × 维度”裁决：显式发型只开放发型维度，显式发色只开放发色维度，未提及的瞳色、体型等仍由该角色的稳定档案提供，不能因为改了一处外貌就放弃整份 Identity。

```text
“爱音和祥子都穿婚纱”
    → 第一次 LLM 为两名角色分别建立 wedding dress 计划
    → 角色档案提供各自身份、发色、瞳色以及缓存衣柜
    → WardrobeAuthority 选中婚纱，并把两人的校服缓存标为 stale
    → 本地 Danbooru 查询核对标签及分类
    → 将裁定结果交给第二次 LLM
```

查询不是万能字典：不可用或失败时，流程会记录状态并继续。角色与服装归属由第一次 LLM 负责，本地查询只负责尽量把候选升级为可信标签。

## 4. 第二次 LLM：在服装权限内输出七段英文结构

`prompt_templates.py` 的 `build_llm_prompt()` 将用户主题、固定角色提示、搜索摘要、服装迁移规则、关键词硬规则和参考图规则填入 `DEFAULT_LLM_PROMPT_TEMPLATE`（也可由 `prompt_builder_template` 自定义）。

随后 `PromptPipeline` 调用 AstrBot 的 `context.llm_generate()`。实际使用哪个模型由当前会话 provider 或 `prompt_builder_provider_id` 决定。第二次 LLM 收到完整用户原文、逐角色 `resolved / explicit_but_unresolved / unspecified` 状态、数据库可信服装下限、未绑定来源证据以及本次禁止恢复的 stale/removed 项。命名套组和来源角色组件都不是封闭白名单；第二次 LLM 负责最终绑定和补全，程序只保留可信下限并过滤确定冲突。系统提示词还要求只输出英文、不要解释、不要 Markdown、不要质量词和画师词，并严格输出七个花括号块。

目标格式如下（实际值由 LLM 根据中文填写）：

```text
{Count: 1girl}
{Characters: }
{Copyright: }
{Identity: a girl with pink hair and grey eyes}
{Details: holding an umbrella, wearing a raincoat}
{Tags: full body, rainy night, wet pavement, city street}
{Nltags: a pink-haired girl standing under an umbrella on a rainy night}
```

| 字段 | 放什么 | 作用 |
| --- | --- | --- |
| `Count` | `1girl`、`2girls`、`1boy`、`no humans` 等 | 先明确人数/性别 |
| `Characters` | 已知作品角色的标准 Danbooru 角色名 | 角色身份与外观描述分离，便于核对 |
| `Copyright` | 角色所属作品 tag | 避免同名角色混淆 |
| `Identity` | 每位角色固有可见特征 | 发色、瞳色、标志性特征等 |
| `Details` | 本次服装、动作、道具等 | “穿什么、做什么” |
| `Tags` | 构图、光影、场景、其他画面 tag | 主体以外的视觉内容 |
| `Nltags` | 简短英文自然语言补充 | 复杂关系、动作方向或细节 |

### 人数与背景的特殊规则

`Count` 应与 `Characters` 中的角色数对应；无人物写 `no humans`。解析时插件会修复不合理的人数 tag。当前 Anima 规则中，扶她（futa）计入女生人数：一名女性加一名扶她是 `2girls, futa with female`，不是 `2girls, futanari`；单独扶她可写 `1girl, futanari`。

对于文本生图，模板还会追加背景策略：用户明确说了地点、环境、天气、场景时保留场景；否则使用白底/立绘策略。LLM 必须在最后放一个背景控制标记供 `prompt_background.py` 读取。该标记不是最终给 ComfyUI 的 tag，参考图或搜索里的背景也不算用户明确要求。

## 5. LLM 返回后的解析、重试与校正

LLM 回应不是原样转发。`PromptPipeline` 会依次处理：

1. **拒绝与空回复**：中文拒绝语会停止任务；若深度思考耗尽输出预算导致空内容，会先关闭深度思考重试一次。仍为空则停止，避免把原始中文误发给 ComfyUI。
2. **七段解析**：`extract_structured_prompt()` 读取七块；格式不对时以更严格规则再请求一次。仍不合规时走兼容的非结构化处理，尽力取出英文 tag。
3. **角色核对**：对角色核心 tag 调用 `resolve_detailed()`，尽量修正为可信的标准 Danbooru 名称，并补作品/核心外观 tag。
4. **服装权限统一裁定**：`WardrobeAuthority` 为本次请求汇总 `cached_tags`、`explicit_tags`、`selected_tags`、`source_grounding_tags` 和 `stale_cached_tags`。同一 cosplay 来源的其他可信服装证据进入 `source_grounding_tags`，可辅助第二次 LLM 补全但不会自动全量注入；穿着者未选中的默认衣柜才进入 stale。已有逐角色计划时，请求级 `outfit_summary` 会被抑制；陈旧缓存会同时从第二次 LLM 上下文、`Identity`、`Details`、`Tags`、`Nltags`、`required_profile_tags` 和 `required_core_tags` 中移除。
5. **外貌逐维度裁定**：发色、头发长度、发型、瞳色、肤色、胸部尺寸、兽耳、尾巴和角等稳定外观不参与衣柜竞争。用户原文只覆盖点名角色明确修改的维度，其他维度继续取目标角色档案；固定角色旧提示在进入第二次 LLM 前与当前档案对齐，第二次 LLM 返回后再删除冲突 Identity 描述并重建角色级外貌。
6. **背景意图落实**：读取控制标记，再以用户原文为准纠正；无背景要求走白底/立绘，有明确场景则保留场景。
7. **可选低 CFG 约束**：`low_cfg_harness_enabled` 开启时，可再让 LLM 生成英文 JSON 约束，用于加权重要样式词、提高优先级或移除冲突 tag。
8. **标签清洗**：`tag_cleaner.py` 分割逗号、去重、过滤不该由 LLM 输出的质量词/画师词，并处理角色与多角色保护。

## 6. 拼成最终英文正向提示词

`prompt_builder.py` 的 `build_final_prompt()` 是最终组装点，不是翻译器，而是“排版员”。常见顺序可理解为：

```text
质量前缀
  + Count / 核心角色 / 作品
  + 画师 tag 与样式 tag
  + 清洗后的内容 tag
  + Identity、Details 等英文描述块
  + Nltags: 英文自然语言补充
```

结构化模式会保留 `Count → Characters → Copyright → Identity → Details → Tags` 的语义顺序，避免把英文自然语言错当普通逗号 tag 清洗掉。固定角色、默认质量词、画师组、样式预设主要在此阶段由本地配置加入，因此 LLM 不应重复输出它们。服装还有一条最终不变量：本次未被选中的已知缓存衣柜不能通过任何结构化字段或 required tag 通道重新进入最终 prompt。

最终字符串会写进本次任务的 prompt summary。启用 `debug_prompt_enabled=true` 后，日志会输出“给 LLM 的任务书”和“最终提示词”，两者不要混淆。

## 7. 英文提示词怎样进入 ComfyUI

完成组装后，调用链是：

```text
comfyui_runtime.py
  → agent_tools/comfyui_agent.py generate --prompt <最终英文提示词>
  → agent_tools/comfyui_operations.py generate_payload()
  → agent_tools/comfyui_workflows.py workflow()
```

`comfyui_operations.py` 同时读取尺寸、步数、CFG、随机 seed 和**独立的负向提示词**，再根据配置选择内置或自定义工作流。

### 内置 `anima_t2i` 工作流

`anima_t2i_workflow()` 的关键连接为：

```text
最终英文正向提示词
  → 节点 11：CLIPTextEncode.inputs.text
  → 节点 19：KSampler.inputs.positive

配置中的 negative_prompt
  → 节点 12：CLIPTextEncode.inputs.text
  → 节点 19：KSampler.inputs.negative
```

采样结果经 VAE 解码并保存。正向、负向是独立通道；本文详述的是正向通道。

### 自定义工作流

当 `custom_workflow_enabled=true` 时，插件读取 `custom_workflow_path` 的 ComfyUI API JSON，不要求节点编号固定为 11/12。它从 `KSampler` / `KSamplerAdvanced` 的 `positive`、`negative` 连线向上追踪，找到对应的 `*TextEncode` 节点，然后：

- 将最终英文正向提示词写入全部正向文本编码节点的 `inputs.text`；
- 将负向提示词写入全部负向文本编码节点的 `inputs.text`；
- 设置 seed；依配置决定是否覆盖尺寸、steps、CFG、采样器和 scheduler。

找不到正向或负向文本编码节点，或同一节点被判为正负两边时，插件会报错而不提交含糊的工作流。

最后 `ComfyUIHistoryRunner` 向 `${comfyui_base_url}/prompt` 发送 `{ "prompt": 工作流JSON, "client_id": 随机ID }`，取回 `prompt_id` 后轮询 `/history/{prompt_id}`，再经 `/view` 下载产物并交给聊天平台发送。

## 不常用兼容命令 `/anm multi_person` 的差异

现在多个角色推荐直接使用普通 `/anm generate <多个角色的描述>`，通过上文七段协议和 `Count`、`Characters` 明确人数。`/anm multi_person` 是不常用的兼容命令；它会在主转换前先让 LLM 产出结构化“多人场景计划”，插件逐个角色作 Danbooru 解析、渲染角色块，再调用同一最终组装器。多人计划失败时会停止本次生成，**不会悄悄退化成单人提示词**。

## 绕过、失败与常见现象

| 现象 | 最可能原因 | 实际行为 |
| --- | --- | --- |
| ComfyUI 收到中文 | 关闭优化或用了 raw/原样模式 | 设计上的直通，不翻译 |
| 本次没有出图 | LLM 中文拒绝或空内容 | 停止，避免发送无效中文 |
| 角色名不对 | 名称歧义、角色不存在或 Danbooru 无证据 | LLM 提候选，本地查询尽力校正；摘要会记状态 |
| 背景变白底 | 用户原文未明确地点/环境 | 默认立绘策略生效；参考图背景不算明确要求 |
| 人工词没被翻译/清洗 | 写在 `#` 后 | 尾缀原样插回 |
| 画师/质量词与 LLM 内容不同 | 本地预设在后面追加 | 这些主要由配置决定 |

## 调用次数并不固定

正常优化至少有一次“主提示词 LLM”调用。还可能有：

| 调用 | 条件 | 用途 |
| --- | --- | --- |
| 第一次 LLM（语义规划） | 正常优化且语义规划接口存在 | 识别角色、共享范围和逐角色服装；提出可验证候选 |
| 第二次 LLM（提示词写作） | 正常优化 | 在已裁定服装权限内输出七段英文结构 |
| 主提示词重试 | 格式不合规或深度思考后空回复 | 修格式或关闭深度思考再试 |
| 服装摘要 LLM | 服装迁移、有搜索上下文、无本地摘要 | 总结服装 tag |
| 角色候选 LLM | 非结构化兼容路径且角色未解析 | 为本地查询提供有限候选 |
| 低 CFG 约束 LLM | 对应开关开启 | 生成加权/移除约束 |
| 多人计划 LLM | `/anm multi_person` | 先拆多人关系 |

所以中文转英文不是固定只调用一两次：主转换是一条调用，外围校验/规划是否执行取决于配置、本地工具和用户文字。

## 如何核对某张图最终发了什么

1. 临时开启 `debug_prompt_enabled`，复现一次请求。
2. 看 `semantic planner LLM output`：这是第一次 LLM 的完整原始 JSON 回复；再对照 `parsed anchors`、`parsed character plans before recovery` 和 `effective character plans after recovery`，判断关系是未输出、被解析拒绝，还是由程序恢复。
3. 看 `prompt builder LLM prompt` 日志：这是给第二次 LLM 的中文任务书，**不是**最终咒语。
4. 看 `prompt builder final prompt` 日志：这是最终交给 ComfyUI 的英文正向提示词。
5. 若用了 `#`，确认它位于最终文本的 `Nltags:` 前，且内容没有翻译。
6. 若启用自定义工作流，确认 JSON 存在从采样器 `positive` / `negative` 连出的文本编码节点。
7. 查看最近任务摘要，其中会有 `semantic_plan_raw`、`semantic_character_outfits`、`explicit_wardrobe_evidence`、`wardrobe_source`、`wardrobe_authority`、`outfit_summary_source`、`final_prompt_head` 和错误原因。

## 一句话总结

**正常情况下，第一次 LLM 判断角色及逐角色服装归属，角色档案和可选查询提供证据，`WardrobeAuthority` 统一裁定本次衣柜，第二次 LLM 在该权限内生成英文七段内容；同一权限继续约束后处理，最终字符串再写入 ComfyUI 的正向文本编码节点。**
