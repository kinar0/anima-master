# 从用户中文描述到 ComfyUI 英文正向提示词

> 本文按当前插件代码整理，说明一次普通“文本生图”请求中，中文怎样变成最终交给 ComfyUI 的英文正向提示词。它面向不熟悉代码的维护者：前四节讲大方向，后半部分适合排查和改配置。
>
> 范围：`/anm generate`（及“生图 / 画图”别名）和 `/anm multi_person` 的文本生图链路。改图、反推咒语、验图重试有共用部分，但不是本文主线。

## 结论先行

插件**没有一个把中文逐字翻成英文的独立翻译器**。正常优化路径分为两个 LLM 阶段：第一次 LLM 是“语义规划器”，负责识别可见角色、判断“谁穿什么”，并把“两人都穿婚纱”这类共享范围展开到每个角色；第二次 LLM 是“提示词写作者”，在本地服装权限已经确定后输出英文七段结构。角色数据库提供身份、稳定外观和候选衣柜，`WardrobeAuthority` 再从用户要求、规划结果和缓存中裁定本次允许或必须删除的服装标签。

```text
中文请求
  → 第一次 LLM 判断角色与逐角色服装归属
  → 角色档案 / 可选 Danbooru 查询提供证据与候选
  → WardrobeAuthority 选中本次服装并标记陈旧衣柜
  → 第二次 LLM 输出英文七段结构
  → 同一服装权限过滤并拼入质量/画师/角色预设
  → 英文正向提示词（--prompt）
  → ComfyUI 正向文本编码节点
  → KSampler 出图
```

因此，ComfyUI 收到的是英文正向提示词；**正常优化路径下不会把中文原句直接交给 ComfyUI**。例外是关闭优化或使用 raw（原样）模式，见“绕过与失败分支”。

## 三种容易混淆的“提示词”

| 名称 | 谁使用 | 内容 | 是否直接给 ComfyUI |
| --- | --- | --- | --- |
| 用户原始提示词 | 用户、插件 | 中文描述，例如“画一个雨夜撑伞的粉发女孩” | 否（正常路径） |
| LLM 任务书 | 插件调用 LLM 时 | 中文规则 + 用户原文 + 检索/角色等上下文 | 否 |
| 最终正向提示词 | ComfyUI | 英文 tag、英文描述、质量/画师/角色预设、`Nltags` | 是，作为 `--prompt` |
| 负向提示词 | ComfyUI | 例如低质量、低分数等要避免的内容 | 是，但不经过本流程 |

Danbooru tag 可粗略理解为模型常见的英文画面关键词，如 `1girl`、`pink hair`、`holding umbrella`。最终内容不必全是严格 tag：`Identity`、`Details`、`Nltags` 可以保留简短英文自然语言，以补足关系和细节。

## 1. 命令进入生成任务

若配置了 `blocked_prompt_combinations`，命令入口先检查用户原始输入。每条规则中的词语全部出现时直接回复拒绝；匹配覆盖 `#` 手工尾缀、raw/原样和多人模式，发生在每日次数扣减、提示词模型与 ComfyUI 调用之前。空规则列表不改变原流程。

命令入口在 `main.py`，动作分发在 `command_actions.py`。普通生图调用 `main.py` 的 `_generate()`，再进入 `GenerationTaskRunner.generate_payload()`（`generation_task.py`）。在真正优化前会做：

1. 检查权限、配额，以及 ComfyUI 是否可连通。
2. 按第一个 `#` 拆文本：前面是交给优化器理解的主描述，后面是用户强制保留的手工尾缀。
3. 若用户请求参考图，或引用一段旧咒语，先将参考上下文追加到主描述。
4. 调用 `PromptPipeline.build()` 得到最终正向提示词；再将 `#` 尾缀插回、且放在 `Nltags:` 前。

例如：

```text
用户输入：画一个粉发女孩在雨夜撑伞 # cinematic lighting, depth of field

交给优化器的主描述：画一个粉发女孩在雨夜撑伞
最后强制插回的尾缀：cinematic lighting, depth of field
```

`#` 后内容不会被 LLM 翻译、重写或标签清洗。它适合已会写英文 tag 的用户；拼错、写中文或写冲突 tag 时，插件通常不会替你修复。

## 2. `PromptPipeline` 的本地预处理

核心入口是 `prompt_pipeline.py` 的 `PromptPipeline.build()`。它先整理输入，再决定需要哪些辅助信息。

### 2.1 清洗与预设

- 删除旧式 `--自由发挥`、`--创意拓展` 等标志，整理重复逗号和空白。
- 识别 `-s1`、`-s2` 等画师组选择器；选择器从用户描述中移走，改为选择配置里的画师预设。
- 通过 `apply_config_preset()` 读取配置预设；预设可同时改变质量词、画师词、工作流等默认项。

### 2.2 两种“不会翻译”的直通情况

| 情况 | 触发方式 | 结果 |
| --- | --- | --- |
| 关闭提示词优化 | `prompt_optimize_enabled=false` | 清洗后的用户文本直接返回，可能仍是中文 |
| raw / 原样模式 | `原样`、`直接画`、`不优化` 等前缀（`strip_raw_prefix()` 识别） | 去掉前缀后直接返回，适合自己写英文 tag |

这两条分支不调用 LLM，也不拼默认质量词/角色词。若 ComfyUI 文本编码器不擅长中文，出图质量可能下降。

### 2.3 从中文中识别的辅助意图

未绕过时，插件会准备以下上下文：

- **固定角色**：`fixed_characters` 中命中的角色名称及其保存的标签/外观提示。
- **角色视觉档案**：解析器提供的角色核心 tag、外观档案、默认服装证据。
- **关键词规则**：配置中为某些中文词设置的硬性提示词要求。
- **感性模式**：命中相关词时，提醒 LLM 不要把用户明确要求的透明材质、表情、姿势等弱化成普通日常画面。
- **服装迁移**：如“让 A 穿 B 的衣服”；识别来源、目标和明确改动，避免把来源角色本人错误搬进图里。
- **背景意图原文**：保留追加参考上下文前的用户文字，后面以它为准判断用户是否真的要求背景。

## 3. 第一次 LLM 语义规划与可选 Danbooru 验证

这一步不直接生成最终咒语，而是给后续英文输出增加“有依据的角色/服装/作品标签”。其失败通常不阻断普通生图。若 LLM1 完全失败，程序只从本地角色证据恢复目标身份并把明确服装请求标为 `explicit_but_unresolved`。若 LLM1 找到了角色但漏掉“角色穿着／换上……衣物”这类直接关系，宿主会阻止该角色回退到默认衣柜；已确认的命名套组可按穿着者绑定，普通衣物保持未解析并交给 LLM2 根据原文处理。

### 3.1 用户要求联网或深度思考

`prompt_research.py` 会检查中文关键词：

- 出现“联网、搜索、搜一下、查一下、官方图、设定图、资料”等，且配置允许、Tavily Key 可用时，执行网络搜索；搜索摘要会给提示词 LLM。
- 出现“深度思考、认真想、仔细想、严格还原、高度还原、不要跑偏、核心特征”等，且配置允许时，调用 LLM 时开启深度思考。

联网结果只用于理解角色、服装、动作和视觉符号；模板明确禁止把网页标题、网址或出处写进最终 tags。

### 3.2 先规划角色与服装，再按条件验证标签

只要正常优化路径具备语义规划接口，第一次 LLM 就会运行；它不以本地 Danbooru 查询是否可用为前提。它只输出 `characters`：每项包含原文中的角色实体短语 `name`、与该实体明确构成 `A（B）` 的 `aliases`、明确服装原文或 `null` 的 `clothing`、cosplay/借衣来源或 `null` 的 `clothing_source`、`clothing_changes` 和 `appearance_changes`。`name` 不得包含整段外貌、服装、姿势或动作描述；匿名人物应使用“粉发美少女”“男角色”等实体短语。没说明别名就返回空数组，没说明衣服就返回 `null`，不得按角色常识补全；可见角色不得合并、抽样或省略，当前宿主上限为 22 人。原文明示总人数或可相加的性别人数时，任务书要求 `characters` 数组严格等长，数量不足会作为结构错误修复一次。遇到“双方、两人、都、双女主、both、all”等范围词时，把同一要求展开到所有目标角色。`wardrobe.kind`、内部状态名和候选 tag 不再出现在给 LLM1 的任务书中。

LLM1 不制造 tag、candidate、lookup、`anchor_id`、`target_anchor_id`、group、description 或交叉引用。主机随后把这些可读字段转换成内部 wardrobe/source anchors，并依次尝试角色视觉档案、服装套组词库和 Danbooru resolver；这些内部对象仍保留原有自动学习入口。校验只守住合法 JSON、原文可定位的角色/服装/来源和数组外形，不因“候选 tag 为空”强迫 LLM1 猜测。`appearance_changes` 不进入衣柜计划，也不直接注入最终 tag；它为每条修改输出 `dimension / operation / source_text`：`operation=replace` 表示新值替换旧值，`operation=additive` 表示新旧视觉值共存。`source_text` 优先使用规范化后的原文子串；轻微改写则通过统一的逐句序列相似度与最长公共片段阈值对齐，不再为某个代词或句式写特例。角色名仍须单独在原文中成立，而且主机不会从用户原文正则猜外貌维度。明确的逐角色服装删除、换色等仍会由主机保守解析后补到服装计划中。核心结构损坏时修复一次；旧版没有 `operation` 的 appearance 记录按保守叠加兼容，避免误删档案值；旧版带 candidates/lookups、wardrobe 枚举或 anchors/character_plans 的 JSON 仍只作为兼容输入。

括号英文不会仅因形态像 tag 就建立角色。LLM1 必须把它明确列入同一可见角色的 `aliases`；主机随后独立验证 `name（alias）` 或 `alias（name）` 确实是原文中同一个相邻括号对，才把英文侧升级为未验证角色 anchor，再交给 resolver 查询并允许新角色学习。主机不再用贪婪正则猜 A 的左边界：`《黑夜君临》（Elden Ring Nightreign）的复仇者（revenant）` 可稳定绑定复仇者，而 `巨乳（huge breasts）的粉发美少女` 中的外貌翻译即使被错误填入 aliases，也会因未与 `粉发美少女` 构成同一括号对而被拒绝。作品书名号别名继续进入 copyright 流程。

`danbooru_resolver.py` 随后提供角色身份、稳定外观和缓存的候选衣柜；本地查询可用时再验证已有候选。这里调用的是插件自己的本地 resolver，不是 Codex 会话里的 `danbooru-tags` skill；普通 `context.llm_generate` 也没有给 DeepSeek 暴露 skill/tool。查询不可用只代表跳过标签验证，**不代表跳过第一次 LLM 的服装归属判断**。候选衣柜按角色启用：已有普通衣物、命名套组或来源服装的角色不读取 default；没有基础服装的角色才收到 default 软参考，只有修改没有基础时也以该参考应用修改。衣柜组件会按统一 framing 分类裁剪画外槽位；除“上半身构图”等视域名外，也识别“上半身肖像”“只拍到腰部以上”等最低可见边界。用户构图在 LLM2 前处理，画外组件不会以具体 tag 再写入 LLM2 的服装证据；LLM2 最终选择的头部、上半身、下半身、手足聚焦等构图还会在输出后再次裁剪并重建衣柜权限。

缓存本身分为两类：角色自己的 `character_outfit` 只能由该角色和 qualifier 选择；通用 `named_outfit` 独立保存 Danbooru canonical 服装 tag、别名、variant 与组件，可绑定给任意穿着者。精确命中“羽丘冬季校服”时，主机选择通用 `haneoka_school_uniform` 套组并把组件交给 LLM2，而不是把它解释成高松灯或爱音自己的 winter profile。

默认、官方常服、私服以及 summer / winter / stage 等档案变体按“角色所在分句”分别选择。例如“爱音穿常服，祥子穿默认服装”会为爱音选择 casual、为祥子选择 default，不再用整条请求中的第一个模式覆盖所有角色。角色档案变体按“已确认角色的 `sourceTags` + qualifier”查找，不要求用户把组合别名连续写出来：`千早爱音穿着演出服` 与 `千早爱音穿着千早爱音演出服` 都选择爱音的 stage 档案；`千早爱音站在舞台上`、`演出结束后` 只是场景或时间信息，不会误选 stage。

服装修改使用语义操作而不是中文句式匹配：`remove` 删除衣物，`damage` 保留衣物但改变为破损状态，另有改色、增加和仅保留指定槽位。LLM1 任务书明确列出程序槽位：`upper_body.primary / lower_body.skirt / one_piece.dress / outerwear / headwear / face_accessory.mask / handwear / legwear / footwear / lower_body.all / misc`；无法稳定分类的服装、配饰或组件统一使用 `misc`，不得自造槽位。主机兼容 `removed` 等常见操作形态和 `mask / boots / shoes` 等日常槽位名；其他未知非空槽位也保守归入 `misc`，不再静默丢弃整条修改。`misc` 只清除来源衣柜中无法分类的缓存组件，不会据此删除动作、场景或普通道具 tag；精确删改含义继续由原样传给 LLM2 的 `source_text` 表达。角色/来源数据库只描述未修改的证据；用户修改会在其上形成请求级最终状态。被删除的来源 tag 会从所有允许集合扣除，破损和缺失状态则按穿着者写回 Details；Nltags 只保留 Details 之外的关系、动作方向或场景补充。外貌采用“角色 × 维度”裁决：显式发型只开放发型维度，显式发色只开放发色维度，未提及的瞳色、体型等仍由该角色的稳定档案提供，不能因为改了一处外貌就放弃整份 Identity。

```text
“爱音和祥子都穿婚纱”
    → 第一次 LLM 为两名角色分别建立 wedding dress 计划
    → 角色档案提供各自身份、发色、瞳色以及缓存衣柜
    → WardrobeAuthority 选中婚纱，并把两人的校服缓存标为 stale
    → 本地 Danbooru 查询核对标签及分类
    → 将裁定结果交给第二次 LLM
```

查询不是万能字典：不可用或失败时，流程会记录状态并继续。角色与服装归属由第一次 LLM 负责，本地查询只负责尽量把候选升级为可信标签。

## 4. 第二次 LLM：在服装权限内输出七段英文结构

`prompt_templates.py` 的 `build_llm_prompt()` 将用户主题、固定角色提示、搜索摘要、服装迁移规则、关键词硬规则和参考图规则填入 `DEFAULT_LLM_PROMPT_TEMPLATE`（也可由 `prompt_builder_template` 自定义）。

随后 `PromptPipeline` 调用 AstrBot 的 `context.llm_generate()`。实际使用哪个模型由当前会话 provider 或 `prompt_builder_provider_id` 决定。第二次 LLM 收到完整用户原文、按角色整理好的稳定外貌、衣服证据、用户修改和禁止恢复项；任务书不再重复解释内部枚举。命名套组和来源角色组件是给 LLM2 理解服装的证据，不是最终 hard tag 清单：本地主机不会再把档案的完整 `effective_tags` 自动拼入角色 `Details` 或共享 `Tags`，只负责删除明确冲突、已删除组件和跨角色污染。普通文字中的“A cosplay C”不再进入旧的“单个固定目标角色换装”块，因此双人图不会出现“最终主体必须是固定角色 A”；旧块只保留给明确的参考图/搜索换装流程。

目标格式如下（实际值由 LLM 根据中文填写）：

```text
{Count: 1girl}
{Characters: }
{Copyright: }
{Identity: a girl with pink hair and grey eyes}
{Details: holding an umbrella, wearing a raincoat}
{Tags: full body, rainy night, wet pavement, city street}
{Nltags: a pink-haired girl standing under an umbrella on a rainy night}
```

| 字段 | 放什么 | 作用 |
| --- | --- | --- |
| `Count` | `1girl`、`2girls`、`1boy`、`no humans` 等 | 先明确人数/性别 |
| `Characters` | 已知作品角色的标准 Danbooru 角色名 | 角色身份与外观描述分离，便于核对 |
| `Copyright` | 角色所属作品 tag | 避免同名角色混淆 |
| `Identity` | 每位角色固有可见特征 | 发色、瞳色、标志性特征等 |
| `Details` | 本次服装、动作、道具等 | “穿什么、做什么” |
| `Tags` | 构图、光影、场景、其他画面 tag | 主体以外的视觉内容 |
| `Nltags` | 简短英文自然语言补充 | 复杂关系、动作方向或细节 |

### 人数与背景的特殊规则

`Count` 统计画面中所有可见人物；`Characters` 只列能确认 canonical 名称的角色。命名角色齐全时两者人数应对应；匿名、裁切或被景深遮蔽的人物可以只由 `Count` 计数，让 `Characters`、`Identity`、`Details` 留空，并把可见信息写入 `Tags` / `Nltags`。只有确实无人物才写 `no humans`。解析时插件会按加法核对混合性别人数，例如 `1girl, 1boy` 合计两人，不会再因单个 tag 不等于总人数而误判。模型若只写与非空 roster 一致的裸数字（例如 `2`），主机会无损归一化为 `2people`。Identity/Details 接受 `A: ... | B: ...` 和分号分隔，但角色名只用于尽力确定归属，不是整份输出有效性的硬门槛：`photo one shows hatsune_miku...` 可按唯一角色名归给 Miku；没有角色名的后续分号句继承上一明确角色；仍无法归属的片段会原样保留到 `Nltags`，不会静默丢弃或令整份回复失败。提示词仍要求每个命名角色段以准确 canonical 名开头，以尽量减少歧义。非空 roster 与 Count 真正不一致时才修复为 `Npeople`。

扶她计数规则不再常驻于每次 LLM2 任务书。只有用户正向明确要求扶她时，任务书才追加 Anima 专用语义：扶她计入女生人数，一名女性加一名扶她使用 `2girls, futa with female`，单独扶她使用 `1girl, futanari`，扶她加男性使用 `futa with male`。普通自慰、色情、胸部尺寸以及“不是扶她”等否定表达都不构成正向证据。结构化回复解析后还有同一请求级来源门控；未经用户正向要求的扶她与男性生殖器内容会从 Count、Identity、Details、Tags 和 Nltags 移除，再进入后续组装。

对于文本生图，模板还会追加背景策略：用户明确说了地点、环境、天气、场景时以用户要求为准；未指定时允许 LLM 选择合适场景，只有 LLM 也没有给出具体环境才使用白底/立绘。LLM 必须在最后放一个背景控制标记供 `prompt_background.py` 读取；实际场景 tag 或叙述与默认白底冲突时，场景优先。该标记不是最终给 ComfyUI 的 tag，参考图或搜索里的背景也不算用户明确要求。

## 5. LLM 返回后的解析、重试与校正

LLM 回应不是原样转发。`PromptPipeline` 会依次处理：

1. **拒绝与空回复**：中英文明确拒绝语都会停止任务；若深度思考耗尽输出预算导致空内容，会先关闭深度思考重试一次。仍为空则停止，避免把原始中文误发给 ComfyUI。
2. **七段解析**：`extract_structured_prompt()` 读取七块。硬校验要求七个字段完整、同名字段没有相互冲突的值、且 `Count` 含有效人数锚点；模型或 provider 原样重复某个字段时只取第一份，内容不同仍按重复字段报错。Identity/Details 的角色归属采用宽松、无损解析。真正结构不合规时，重试任务书会列出具体错误并附上第一次回复，再正常请求 LLM2 重写；重试后仍不合规才以 `invalid_structured_prompt` 中止。调试摘要分别保存 `prompt_llm_initial_content`、`prompt_llm_retry_content`、两次校验错误和最终采用的 attempt，避免把初稿误认为 final prompt 的直接来源。合法七段输出视为主要语义来源：共享 `Tags` 只删除确定的质量词、画师词、精确重复项、用户明确移除的衣物槽位和已知陈旧衣柜，不再用模糊衣物/外貌关键词重解释动作、道具、镜头或场景，也不应用旧的 65 项截断。
3. **角色核对**：本地档案确定的 owner 候选若与已确认 tag 精确一致，会绑定回对应可见角色 anchor；查询未命中不应使已知角色变成 unresolved。LLM2 收到“原文名字 → canonical 身份”映射。解析后先保留精确身份匹配，再校正唯一匹配的名字；完整 roster 只剩一名未知与一个缺失身份时，按唯一剩余对应替换，并同步更新 Identity、Details、Nltags。若仍缺少已确认的可见身份，则触发同一次结构重试；重试仍失败时停止生成，不按位置猜测多名未知角色。其他未确认名字继续走 `resolve_detailed()` 的兼容核对。
4. **服装权限统一裁定**：`WardrobeAuthority` 为本次请求汇总 `cached_tags`、`explicit_tags`、`selected_tags`、`source_grounding_tags` 和 `stale_cached_tags`。同一 cosplay 来源的其他可信服装证据进入 `source_grounding_tags`，可辅助第二次 LLM 补全但不会自动全量注入；穿着者未选中的默认衣柜才进入 stale。已有逐角色计划时，请求级 `outfit_summary` 会被抑制；陈旧缓存会同时从第二次 LLM 上下文、`Identity`、`Details`、`Tags`、`Nltags`、`required_profile_tags` 和 `required_core_tags` 中移除。
5. **外貌逐维度裁定**：发色、头发长度、发型、瞳色、肤色、胸部尺寸、兽耳、尾巴和角等稳定外观不参与衣柜竞争。固定角色旧提示在进入第二次 LLM 前与当前档案对齐。只有 LLM1 的同角色、可定位 `appearance_changes` 会开放对应维度；是否替换旧值完全读取 LLM1 的 `operation=replace/additive`，主机不再扫描“染上/变成”等具体中文关键词。其他维度继续使用角色档案。第二次 LLM 已正确表达且与档案一致的稳定特征保留为自然语言，只补它遗漏的稳定维度，不再把整份 Identity 盲目追加到最终提示词末尾。主机不会从用户原文正则猜测“改眼睛/发型/角”等维度。第二次 LLM 返回后，权限仍过滤没有 LLM1 修改提示的冲突 `Identity` 猜测、角色 `Details` 和共享 `Tags`。`Identity` 合并还会保留 writer 的谓词边界：`has pink hair … and is a loli` 会规范为 `is a loli and has …`，不会生成 `has is a loli`。`Nltags` 中重复或猜测的外貌句仍会移除。
6. **背景意图落实**：读取控制标记，再以用户原文为准纠正；用户明确指定的背景优先。没有指定背景时，模型若写出具体环境则保留它，并移除与之冲突的自动 `simple background / white background`；模型也没有给出场景时才使用白底立绘。NAI `-r` 最终规划若新增场景，同样移除自动白底。
7. **可选低 CFG 约束**：`low_cfg_harness_enabled` 开启时，可再让 LLM 生成英文 JSON 约束，用于加权重要样式词、提高优先级或移除冲突 tag。
8. **标签清洗**：合法七段路径只做保守的格式整理、质量词/画师词过滤和精确去重；旧平铺/非结构化回退才继续使用较强的同义冲突处理与内容数量上限。衣柜冲突按已经确认的具体 tag 或用户删除槽位处理，不能因为 `skirt lift`、`shirt tug`、`hair ornament` 等词含衣物或外貌字样就整项删除。

## 6. 拼成最终英文正向提示词

`prompt_builder.py` 的 `build_final_prompt()` 是最终组装点，不是翻译器，而是“排版员”。常见顺序可理解为：

```text
质量前缀
  + Count / 核心角色 / 作品
  + 画师 tag 与样式 tag
  + 清洗后的内容 tag
  + Identity、Details 等英文描述块
  + Nltags: 英文自然语言补充
```

结构化模式会保留 `Count → Characters → Copyright → Identity → Details → Tags → Nltags` 的语义顺序，避免把英文自然语言错当普通逗号 tag 清洗掉。为方便在 ComfyUI 中阅读，各语义块分行显示，但块间仍使用 `,\n`，即上一行保留逗号，换行只负责排版。内部已确认 tag 在显示时还会把字面量冒号、圆括号和方括号转义，例如 `s:p_little_knight` 输出为 `s\:p little knight`、`character_(series)` 输出为 `character \(series\)`；权重表达式如 `(watercolor:2)`、以及角色描述内的 `(flat chest:1.4)` 则保留其语法。转义是幂等的，不会重复处理已有反斜杠。Identity/Details 已表达的自然语言会从 Nltags 去重；若 Nltags 没有额外内容则整块省略。resolver 的 `missing_descriptions` 只作为 LLM2 理解原文的上下文，主机绝不再把其中的中文原句直接追加到最终 `Nltags`。服装叙述过滤只删除实际的穿着/裸体断言，不能因为动作或性征描述用裙子等衣物定位（如 `erection beneath her skirt`）就删除整句。固定角色、默认质量词、画师组、样式预设主要在此阶段由本地配置加入，因此 LLM 不应重复输出它们。服装还有一条最终不变量：本次未被选中的已知缓存衣柜不能通过任何结构化字段或 required tag 通道重新进入最终 prompt。`#` 后手工尾缀仍按用户提供的权重/转义语法原样插回。

最终字符串会写进本次任务的 prompt summary。启用 `debug_prompt_enabled=true` 后，日志会输出“给 LLM 的任务书”和“最终提示词”，两者不要混淆。

## 7. 英文提示词怎样进入 ComfyUI

完成组装后，调用链是：

```text
comfyui_runtime.py
  → agent_tools/comfyui_agent.py generate --prompt <最终英文提示词>
  → agent_tools/comfyui_operations.py generate_payload()
  → agent_tools/comfyui_workflows.py workflow()
```

`comfyui_operations.py` 同时读取尺寸、步数、CFG、随机 seed 和**独立的负向提示词**，再根据配置选择内置或自定义工作流。

### 内置 `anima_t2i` 工作流

`anima_t2i_workflow()` 的关键连接为：

```text
最终英文正向提示词
  → 节点 11：CLIPTextEncode.inputs.text
  → 节点 19：KSampler.inputs.positive

配置中的 negative_prompt
  → 节点 12：CLIPTextEncode.inputs.text
  → 节点 19：KSampler.inputs.negative
```

采样结果经节点 19（KSampler）→ 节点 47（解码前清理显存占用）→ 节点 8（VAE 解码）→ 节点 46（解码后清理显存占用）→ 节点 9（保存图片）。两次清理均使用 EasyUse `easy cleanGpuUsed`，通过输入输出连线保证执行顺序；解码前节点传递采样 latent，解码后节点传递图片。内置工作流要求 ComfyUI 安装 ComfyUI-Easy-Use；图生图复用该输出链。仓库的 `anima_api.json` 同样在解码前后各串入一个清理节点。其他自定义工作流仍按各自 JSON 的连线执行，不自动插入节点。清理用于尝试缓解内存压力，不保证解决解码卡顿，也不能解除已经卡住的任务。正向、负向是独立通道；本文详述的是正向通道。

### 自定义工作流

当 `custom_workflow_enabled=true` 时，插件读取 `custom_workflow_path` 的 ComfyUI API JSON，不要求节点编号固定为 11/12。它从 `KSampler` / `KSamplerAdvanced` 的 `positive`、`negative` 连线向上追踪，找到对应的 `*TextEncode` 节点，然后：

- 将最终英文正向提示词写入全部正向文本编码节点的 `inputs.text`；
- 将负向提示词写入全部负向文本编码节点的 `inputs.text`；
- 设置 seed；依配置决定是否覆盖尺寸、steps、CFG、采样器和 scheduler。

找不到正向或负向文本编码节点，或同一节点被判为正负两边时，插件会报错而不提交含糊的工作流。

对于 NAI 的 `NovelAIGenerator`，工作流适配器改为追踪 `prompt` /
`negative_prompt` 的字符串连线，支持直接文本、`Textbox` 和
`ComfyUIToNovelAIV4`。最终字符串写入转换前的输入，转换节点继续负责 NAI
权重语法；不要求存在 KSampler 或 TextEncode。普通语义 LLM1、角色衣柜权限、
LLM2、raw 和 `#` 尾缀处理均沿用上述流程。不带 `-r` 时只传整体提示词；
正文中单独出现 `-r` 时，先完成普通证据与最终提示词，再让模型分析视角、
人物关系、实际画布的宽高比例和整体布局，最后按所选模型上限为可见角色实例给出
位置理由与 0–1 空间坐标（V5 文生图最多 22 个，V4/V4.5 最多 6 个）。原文明确涉及人物间动作时，同一次规划还可输出每个实例的
`interaction_tags`：例如主动拥抱者为 `source#hug`，被拥抱者为
`target#hug`，相互拥抱时双方均可用 `mutual#hug`。掀门帘等单人动作不要求方向标签；主机只接纳每项
`#` 后为单个动作 tag 的有效项，丢弃畸形项但保留布局；全局提示词中的方向
标签会被移除。这些标签是在用户 `#` 手工尾缀拆分之后由布局规划产生的。
同一角色在不同格子中重复出现按多个实例处理，主机不按姿势词强制改写坐标。
质量词、画师、总人数、背景和共享场景保留在原正向输入；无数字性别、角色身份、
外貌、服装、表情、姿势、动作、物件使用和人物与环境的局部关系经独立转换节点
进入 `CharacterPromptSelect`，再接到 NAI 生成节点。共享环境物件不会只因也在
角色框中出现就从全局删除；例如 `bed` 可留在 base，`lying on bed` 属于角色。规划失败
或使用非 NAI 工作流时停止提交。具体开关、尺寸和采样参数见[NAI 配置](configuration.md#novelainai工作流)。
布局模型重写全局提示词后，若本次启用了画师词，主机按画师组选择补回配置中的画师串；
同名但被模型改坏的画师项会由配置值替换。带名称消歧括号的加权画师项，
例如 `(yd_(orange_maru):1.1)`，在最终显示时保留配置中的下划线、括号和权重。

最后 `ComfyUIHistoryRunner` 向 `${comfyui_base_url}/prompt` 发送 `{ "prompt": 工作流JSON, "client_id": 随机ID }`，取回 `prompt_id` 后轮询 `/history/{prompt_id}`，再经 `/view` 下载产物并交给聊天平台发送。

## 不常用兼容命令 `/anm multi_person` 的差异

现在多个角色推荐直接使用普通 `/anm generate <多个角色的描述>`，通过上文七段协议和 `Count`、`Characters` 明确人数。`/anm multi_person` 是原作者留下的独立 2–4 人兼容路线：它在进入普通 LLM1 之前分流，直接用自己的多人 planner 生成无角色名依赖的 Character A/B/C/D 特征块，逐个执行候选与 Danbooru 校正，再作确定性构图和最终组装。它**不调用普通语义 LLM1，不读取角色视觉档案，也不套用普通路径的 `WardrobeAuthority`**；人物服装以多人 planner 各人物块为准。多人计划失败时会停止本次生成，**不会悄悄退化成单人提示词**。

## 绕过、失败与常见现象

| 现象 | 最可能原因 | 实际行为 |
| --- | --- | --- |
| ComfyUI 收到中文 | 关闭优化或用了 raw/原样模式 | 设计上的直通，不翻译 |
| 本次提示 `no_chat_provider` | 当前会话和指定配置都没有可用 LLM provider | 停止，不把中文原文当作英文 tags 提交 |
| 本次没有出图 | LLM 中英文拒绝或空内容 | 停止，避免发送无效内容 |
| 角色名不对 | 名称歧义、角色不存在或 Danbooru 无证据 | LLM 提候选，本地查询尽力校正；摘要会记状态 |
| 背景变白底 | 用户和 LLM 都未给出具体地点/环境 | 默认立绘策略生效；参考图背景不算明确要求 |
| 人工词没被翻译/清洗 | 写在 `#` 后 | 尾缀原样插回 |
| 画师/质量词与 LLM 内容不同 | 本地预设在后面追加 | 这些主要由配置决定 |

## 调用次数并不固定

正常优化至少有一次“主提示词 LLM”调用。还可能有：

| 调用 | 条件 | 用途 |
| --- | --- | --- |
| 第一次 LLM（语义规划） | 普通优化且语义规划接口存在；不含 `/anm multi_person` | 只输出逐角色服装/外貌意图，不猜 tag |
| 第二次 LLM（提示词写作） | 正常优化 | 在已裁定服装权限内输出七段英文结构 |
| 主提示词重试 | 格式不合规或深度思考后空回复 | 修格式或关闭深度思考再试 |
| 服装摘要 LLM | 服装迁移、有搜索上下文、无本地摘要 | 总结服装 tag |
| 角色候选 LLM | 非结构化兼容路径且角色未解析 | 为本地查询提供有限候选 |
| 低 CFG 约束 LLM | 对应开关开启 | 生成加权/移除约束 |
| 多人计划 LLM | `/anm multi_person` | 独立拆分 Character A/B/C/D；不经过普通 LLM1 |

所以中文转英文不是固定只调用一两次：主转换是一条调用，外围校验/规划是否执行取决于配置、本地工具和用户文字。

## 如何核对某张图最终发了什么

1. 临时开启 `debug_prompt_enabled`，复现一次请求。
2. 看 `semantic planner LLM output`：这是第一次 LLM 的紧凑 JSON 原文；主机随后才生成内部 anchors/character plans。对照解析日志可判断关系是未输出、被拒绝，还是由主机完成结构转换。`/anm multi_person` 不应出现这次调用。
3. 看 `prompt builder LLM prompt` 日志：这是给第二次 LLM 的中文任务书，**不是**最终咒语。
4. 看 `prompt builder final prompt` 日志：这是最终交给 ComfyUI 的英文正向提示词。
5. 若用了 `#`，确认它位于最终文本的 `Nltags:` 前，且内容没有翻译。
6. 若启用自定义工作流，确认 JSON 存在从采样器 `positive` / `negative` 连出的文本编码节点。
7. 查看最近任务摘要，其中会有 `semantic_plan_raw`、`semantic_character_outfits`、`explicit_wardrobe_evidence`、`wardrobe_source`、`wardrobe_authority`、`outfit_summary_source`、`final_prompt_head` 和错误原因。

| ComfyUI 工作流和正负提示词写入 | `agent_tools/comfyui_operations.py`、`agent_tools/comfyui_workflows.py` |
| API 提交、轮询、图片下载 | `agent_tools/comfyui_history.py`、`agent_tools/comfyui_http.py` |

## 一句话总结

**正常情况下，第一次 LLM 判断角色及逐角色服装归属，角色档案和可选查询提供证据，`WardrobeAuthority` 统一裁定本次衣柜，第二次 LLM 在该权限内生成英文七段内容；同一权限继续约束后处理，最终字符串再写入 ComfyUI 的正向文本编码节点。**


自由命名衣橱、独立 owner/source 字段以及完整造型标签的精确学习规则，见 [自由命名衣橱与完整造型标签](角色与服装配置工作流.md#自由命名衣橱与完整造型标签2026-09-12)。
