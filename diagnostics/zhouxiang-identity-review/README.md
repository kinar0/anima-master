# 最近粥祥身份识别波动的定位（2026-10-17）

## 失效环节

请求经过命令分发、手工尾缀拆分、普通优化入口后，先预取本地角色资料，再进行 LLM1 语义规划及 target/source 身份绑定，随后构建逐角色衣柜权限。NAI `-r` 在该处走专用 LLM2 直接实例 JSON；后处理再将实例送往独立转换节点、ComfyUI、图片交付。

这次差异已在 LLM2 之前的 `confirmed_character_bindings` 与 `nai_local_profile_references` 出现，最终错误也已经存在于交给工作流的实例身份中，故定位在角色规划/绑定/验证链，不是图片下载或聊天交付遗漏。raw、手工尾缀与旧独立多人不是这五次的主路径。

### 1. 本地命中资料不等于可见角色已被正确绑定

`bind_confirmed_character_anchors`（`prompt_pipeline.py:343`）只将已有 `target_character` anchor 的候选绑定到确认 tag，不把每条缓存命中都自动变成可见人物。这一边界能保护借衣来源和引述人物，但也意味着 LLM1 漏列、合并或错分类某实体后，缓存虽然命中，权威可见 roster 仍可能只剩两人。

历史数据确定显示后三次没有将“粥祥”正确绑定成独立的已确认 target。由于原始回复没保存，不能进一步断言当次 LLM1 究竟是漏列、合并，还是把它当成其他语义角色。

### 2. 补充参考不是强制名单，还会被已有角色/来源判断过滤

`nai_local_profile_references`（`prompt_pipeline.py:3730`）从缓存恢复被遗漏的身份，但仅作为条件参考。`represented` 汇总已有计划名称和候选；`donors` 汇总 `outfit_source` 名称和候选。`3763` 行只要恢复身份与二者之一有交集就跳过。

按历史保存的档案和原文重放，五次都能恢复 `粥祥 => togawa_sakiko_(master_of_melodia)`，且没有别名 owner 歧义、未确认或命名套组冲突。因此，在当前实现下，后两次没有补充参考的现象落在“被认为已经代表该身份”或“被认为是服装来源”这类内部排除判断；这些内部 anchors/计划未保存，不能从摘要二选一。

中性离线重放证明：若 LLM1 将并列描述中的“粥祥衣服”误绑定为另一人的衣物、并把粥祥列为来源，这条规则确实会滤掉粥祥补充参考，生成与异常任务相同的清单形态。该样例明确标为假设输入，只证明可达的代码失效路径，不能当作历史模型原文。真正只借粥祥衣服、没有让粥祥出场的相邻反例仍应保留此排除，不能简单删除所有 donor 过滤。

### 3. 最终缺人检查只检查第一阶段已确认的 target

`_build_nai_direct_prompt`（`prompt_pipeline.py:5685`）使用 `expected = confirmed_semantic_character_tags(semantic_result)` 检查缺失；这个集合来自已有 target anchor，不包括尚未变成 target 的条件资料。

因此，若前面已经只确认祥子和爱音，writer 仅返回两人就满足检查。即使提供了粥祥条件参考，也不会因为 writer 未采用而失败。若 writer 返回第三个人、但名称直接写成中文“粥祥”，现有实例绑定也可能找不到其本地权限；这条路径没有统一把已知可见别名改为 canonical 的步骤，第三人会作为未匹配实例继续进入工作流。历史 13:58:50 的中文身份和棕发正符合这个缺口。

六组离线重放包括完整三人、条件参考救回第三人、提供参考但 writer 仍省略第三人、假设供衣误分类、假设供衣误分类后返回中文身份，以及合法画外供衣者。全部沿当前生产管线正常两次替身调用完成，断言核对上述差异。它们证明宿主接受边界，不证明历史 LLM 的具体输出，也不是六次真实模型成功。

### 4. 外貌查询另有一个可重复的身份前缀歧义

`saved_appearance_for_names`（`prompt_pipeline.py:1738`）将精确相等和长度至少三的子串匹配混合使用，没有优先保留精确身份。`togawa sakiko` 是 `togawa sakiko (master of melodia)` 的前缀，所以基础祥子和粥祥同在资料中时，查询 `("粥祥", canonical)` 同时命中两份档案，最终返回空身份和空外貌。

五份历史资料都可重复：只按“粥祥”查询能拿到正确档案和外貌；加上已知 canonical 反而返回 `("", ())`。这解释了条件救回身份后仍可能没有正确稳定外貌可用的另一个程序缺陷；它与角色彻底消失的 roster 问题分开，不应混称词库没命中。

## 定位结论与修复边界

可以确定的原因是：**可见 target 规划/绑定不完整，加上条件参考与最终校验缺口，把上游波动放行成缺人或未解析身份；另有基础角色/带后缀身份的外貌查询歧义。** 不是继续添加“粥祥”别名就能解决。

后续应检查独立可见实体的完整性、参考排除的依据、已返回实例的精确别名归一化，以及精确身份优先的外貌查找。不能把所有提及名字强制变成可见人物，也不能让衣物来源变成额外人物；同名多实例、借衣/cosplay、引述和画外角色必须有反例。

当前 `debug_prompt_enabled=false`，历史五次均没保存 LLM1/LLM2 原始输出、内部 anchor 角色和逐角色计划；AstrBot 文件日志也关闭。故“后两次究竟触发哪一种排除”仍不能逐次实证，后续复现应保存这些阶段数据及每条参考的排除原因。此次未更改日志或运行设置。

修复前证据：`historical-identity-evidence.json`；中性输入与实际后处理结果：`offline-replay.json`。当时生产代码为提交 `43c4d4a`。当前 `replay.py` 已更新为修复后断言，写入独立的 `after-fix-*` 文件，不覆盖上述修复前证据。

## 后续修复

- 精确别名/身份匹配优先于旧模糊匹配，基础名不再使明确的后缀身份失去外貌；真正精确冲突仍弃权。
- 保留来源身份的条件事实；出场仍由原文语义决定，不将每条缓存命中升级为人物。实际返回的唯一精确别名归一 canonical 后再过滤自己的外貌和衣物，未表达的维度不补齐。
- LLM2 为未返回的已知名字给出 donor/quoted/offscreen 与原文上下文；初步来源独立出场须给 visible 证据。遗漏、不连续/虚构引用、声明与实例矛盾共用既有一次修复预算，失败不提交。
- 真实压力测试发现，仅增加上述字段仍会让模型沿用错误的来源关系：`after-fix-live/failed-source-authority-bias.json` 保存这个失败。最终补充 system 的原文优先级，并对缺少直接借衣关系证据的首次 donor 排除触发一次独立语义复核；陌生有效表达复核后仍允许，宿主不据词法缺失硬猜出场。
- 摘要保存本地身份提及、内部角色分类、身份核对理由和错误；无需开启全量 debug 也能区分命中、初步角色与最终采用，但不能据此还原完整模型原文。
- 借衣反例还发现模型把两段真实引用以省略号连接，严格连续匹配连续两次拒绝了合法场景；失败记录为 `after-fix-live/failed-excerpt-elision.json`。最终支持精确片段数组，显式省略号也拆成各自验证的引用数组，不构造连续原文，虚构片段仍停止。

离线回归覆盖漏列、误判供衣、直接输出中文别名、基础/后缀身份、同名冲突、借衣/画外/引述、陌生借衣和失败停止，并与既有同名多格、服装修改、互动、文字、工作流等一起运行。没有修改运行档案、配置或重载服务，也没有生成图片。

真实模型阶段使用中性客厅合影、借衣、引用名字和画外说话。`after-fix-live/` 保留中间通过及失败记录：带明示“三人”的两次注入实验先触发已有 LLM1 人数修复，未覆盖新恢复路径，因此不算新机制成功；去掉明示人数后才覆盖条件身份恢复。`after-fix-live-final/` 存放最终实现的验证，包含两次完整合影、三个非出场反例和两次注入不完整第一阶段后调用真实写作者。注入实验不是完整真实两阶段测试。所有记录包含实际任务书、原始回复和最终实例，可核对被过滤的内容；它们不证明图片解剖或所有未来语义判断必然正确。

最终结果：596 项相关离线回归通过；真实模型测试 7 项通过，其中 5 项是完整两阶段、2 项注入不完整 LLM1 后调用真实 LLM2。两次完整合影、两次注入失误都得到基础祥子、粥祥变体、爱音三个正确身份；三个非出场反例均只有基础祥子和爱音。实际首次/修复回复及最终文本逐项核对；合法借衣反例有一次针对来源排除的复核，其余最终实验均无须写作者重试。六组中性离线重放及五份历史资料的精确外貌查询也通过。唯一环境警告为 Python 3.12 的既有 `audioop` 弃用提示。

提示词职责对照：LLM1 的原文意图字段与修复契约未改；专用 LLM2 原有双语层、身份、作品、动作、表情、道具、衣柜、逐实例修改、可见性、空间投影、互动所有权、方向语法与同次复核完整保留。新增身份核对附加于原任务书，system 仅追加出场依据的优先级；修复继承同一完整任务书/system，原文字职责保持，身份与文字共用一次预算。输出新增可条件省略的 `identity_review`，属于本次有意增加的功能契约。普通七字段、raw、手工尾缀、旧多人、工作流提交及聊天交付路径没有改动；共用外貌查询仅改变精确与模糊匹配的优先顺序。
