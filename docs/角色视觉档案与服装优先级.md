# 角色视觉档案与服装优先级

> **严正警告：维护者、AI 和用户本人都不要随便精简或简化 LLM 提示词。** 可见性、逐角色外貌和衣柜权限、显式修改优先级都属于功能契约；不能压成一句“遵守档案”。修改前须按 [提示词维护要求](prompting.md#严正警告不要随便精简或简化给-llm-的提示词) 对照职责并验证。

本文记录角色识别、Danbooru 视觉档案学习和服装修改的现状，供后续维护时参考。

## 当前流程

### 2026-10-19：外貌来源只转移指定维度

`appearance_changes` 可携带原文中的 `reference_character`，与 `clothing_source` 独立。只借发型、瞳色、角等特征不选择来源的衣柜，也不强制来源本人出场；名字仅出现于他人的外貌参考短语时，不成为强制可见名单，原文另有独立出场仍保留。来源必须在该修改的原文引用中，并唯一精确匹配本地角色，才提供对应维度的 canonical 事实；不依名字相似度恢复整份档案。未知或歧义来源保留原始参考关系，禁止据此恢复默认衣柜或猜具体造型。

已知来源、实际写出的可见维度若丢失相应事实，在接收者自己的 Identity/Details 或 NAI 实例 prompt 中校验，复用原有一次写作纠错预算；共享 Tags 或分析字段不能替代归属。不可见维度、独立覆盖的修改、同维度来源冲突不被此校验强补。一般名词翻译仍是可选词汇参考，不因此变成逐项验收清单。NAI 同名多格先按原文绑定实例，再检查各格对应来源。

发型中的 `twintails / ponytail / half-up twin-tail-like` 不属于身体 `tail`；同一句真正的狐狸尾巴仍按独立身体维度受控。发型修改仅允许写作者选择本人的发饰槽位，不自动补发带、不开放来源整套衣柜；明确删发饰仍优先，多人和同名多格不共享该权限。来源档案的作品元数据也不自动成为接收者所属作品。

大头照、证件照、脸部肖像在写作前裁剪默认参考，写作后沿用相同规则。领带、袖子随躯干衣物裁剪；隐式默认整套制服身份不迫使画面展示衣柜，用户明确的命名套组及服装补丁仍受原有保护。被裁剪的组件、禁止槽位和移除记录保留，不能因裁剪后为空就误判缺档案、重建整套默认服装。

1. 普通路径的语义规划 LLM 从用户请求只输出逐角色 `name / aliases / clothing / clothing_source / clothing_changes / appearance_changes`，不看 wardrobe 枚举、不猜 tag；`name` 只允许角色实体短语，匿名人物也不能把整段特征描述当作名字。主机再生成内部 anchors/计划并匹配本地证据。该步骤与 Danbooru 查询是否可用解耦。`/anm 多人` 是独立兼容路线，不进入这套 LLM1、视觉档案和衣柜权限流程。
2. 本地 `danbooru-tags` 在可用时验证候选。角色括号别名必须先由 LLM1 放入同一角色的 `aliases`，再由主机验证 `name（alias）` 或反向形式在原文中精确相邻；通过后才升级为未验证角色 anchor，并可继续查询和学习新角色，不要求本地预先确认。`《黑夜君临》（Elden Ring Nightreign）` 等作品别名进入 copyright 流程。外貌、衣物、动作和场景翻译不会因为位于括号中而进入角色流程。
3. 已确认的目标角色会从 Danbooru 帖子采样，分别学习默认服装 tag 与稳定外观 tag（例如发、瞳、角、耳朵、尾巴、翅膀、伤痕），并保存为角色视觉档案；通过支持度与冲突筛选的服装 tags 不再按固定数量截断。
4. 请求级 `WardrobeAuthority` 合并用户显式要求、每角色计划和候选衣柜，计算本次有效、被修改与失效的服装 tags。
5. 稳定外貌建立独立的角色级权限：固定角色旧提示先与当前视觉档案对齐，用户显式外貌要求只覆盖被点名角色的对应维度。
6. 第二阶段 LLM 仍负责完整理解原文，并按角色生成最终外貌、服装状态、动作、镜头和氛围；数据库证据是补全依据，不是覆盖用户原文的裁决者。
7. 最终提示词阶段不再按角色自动注入整套服装证据，也不再把多人共有档案组件提升为共享 hard tags；服装档案只供 LLM2 理解和供后置冲突过滤。未选中的历史套装身份、明确冲突的组件及用户已删除的来源衣物会被清除。已确认绑定的普通服装由写作者选择可见组件，不能仅因普通衬衫、斗篷等组件也存在于旧档案或另一人的套装中，就当成污染删除；指定套组 canonical tag、制服限制、显式移除和禁止槽位仍受约束。外貌权限仍按角色逐维度重建，并过滤 Identity、角色 Details、共享 Tags 与 Nltags 中未获用户授权的竞争特征；用户明确开放的维度保留本次修改，其他维度恢复目标角色档案。

角色档案与通用套组在存储上也已分离：角色自己的 `character_outfit` 用角色 canonical tag 作为 owner，并按 qualifier 选变体；Danbooru 命名服装使用无穿着者的 `named_outfit`，自行保存 canonical tag、别名、variant 和组件。后者可绑定给任何角色，不参与“目标角色自己的 default/casual/stage 衣柜”选择。

本地词库只验证或筛选候选，不能从中文俗称自行推断角色。对于训练语料覆盖不足的新作品角色，应配置本地别名映射，例如 `哈吉蜗=revenant_(elden_ring)`。

## 服装意图

已绑定的服装来源 canonical tag 必须进入穿着者实际提示词，普通借衣和经过修改的来源服装都保留；不把来源本人追加为可见角色。来源 tag 与可选 `_(cosplay)` 后缀分开，后者仍要求明确 cosplay 关系。来源未确认或没有绑定时不猜。此为 2026-10-20 对此前来源锚点被抑制的修复，详见 [当前服装工作流](角色与服装配置工作流.md#当前提示词工作流)。

2026-10-20：局部剪裁/只保留某件衣物的一部分使用 `modify`，不改变其他衣物的选中权限；全身仅穿某些衣物才使用 `keep_only`。程序拒绝把明确局部保留原文提升为全身 allowlist，未知修改仍保留原文给写作者。仅有 focus 不是裁切证据；全身脚部焦点不会删除上衣和帽子，真实局部特写仍裁剪。括号内明确配饰缺席也参与逐角色删除，供衣者仅在借衣原文中被引用时不作为额外可见人物。详见 [借衣工作流补充](角色与服装配置工作流.md#当前提示词工作流)。

| 用户表达 | 当前意图 |
| --- | --- |
| `官方默认服装`、`原作默认服装`、`默认服装`、`标准服装` | 使用角色普通帖子采样得到的 default 档案。 |
| `官方常服`、`常服`、`casual 套装`、`casual outfit` | 使用角色独立、完整的 casual 档案；必要时以 `角色 tag + casual` 的帖子证据学习，不回退到 default。 |
| `私服`、`居家私服`、`居家服`、`日常便服`、`随意生活服`、`休闲穿搭` | 使用 `creative_fallback`，由最终提示词 LLM 为每个角色设计服装，不注入 default/casual 档案。 |
| `白色卫衣和牛仔短裤`、`连体式泳装`、`分体式泳装` 等具体衣物 | 作为该角色本次实际服装基础；不读取 default，第二阶段按原文生成。 |
| `裙子变蓝色`、`没穿上衣` 等只有修改、没有说明基础 | 读取该角色 default 作为软参考并应用强制修改；若指定了命名服装，则改为在该命名服装上修改。 |
| 没有该角色的任何衣物证据 | 按 `unspecified_wardrobe_policy` 提供 default 软参考或完全创作；其他角色有没有服装证据不影响这一角色。 |

“常服”在这里特指作品中的官方 casual 套装，不等于自由设计的“私服”。需要角色最常见的帖子服装时使用 `默认服装`；希望模型自行设计时使用 `私服` 或 `居家私服`。

多人可以在同一请求中混用这些意图。程序按角色所在分句分别选择 default、casual 或 creative，并按同一局部范围选择 summer、winter、stage 等 profile 变体；一个角色的“常服”不会再把其他角色也切换到 casual。

角色自有变体通过“目标角色 canonical/source tag + qualifier”选择，而不是只靠完整组合别名扫描。例如 `千早爱音穿着演出服` 会选择 `chihaya_anon` 的 `stage` 档案，即使档案触发别名保存为“千早爱音演出服”；单纯“站在舞台上”或“演出结束后”不构成穿着 stage 服装的证据。衣物槽位分类随后才对选中档案执行删除、换色和构图裁剪，它不承担档案选择。

## 设计上的优先级

外貌权限先区分“角色事实”与“本图可见表达”：稳定档案约束实际写出的特征，不要求每个存档特征出现在提示词中。普通 Identity 与 NAI 实例不再补齐未表达的档案维度。背向不露眼可省略瞳色，背向但回头或镜面露眼则由模型保留实际可见特征；同名不同格独立选择。不为露出档案特征而改变用户镜头，也不永久修改 profile。闭眼仍是眼部表情，而看不见的虹膜颜色可以省略，不能把闭眼/无高光一律改成 omit。

NAI 的正确中文外貌应保持原语言，例如“粉色长发灰眼女孩”；宿主现在按已分类片段与档案比较，保留已确认一致的中英文表达，不再一律删除。颜色、长度等复合事实须同时一致，用户已开放的修改维度不受旧值约束；不确定的受控事实继续保守过滤。此改动不新增可见性推断或档案补齐，不把“视角/墙角”等描述当作角色的角，也不修改方向动作 tag。

“不画眼睛 / no visible eyes”等明确不可见要求属于逐角色外貌 `omit` 操作，优先于该角色视觉档案的瞳色。它不同于换色 `replace` 和保留原值的 `additive`；只有瞳色完全不可见时才不再写入档案值。“眼神无光”“闭眼”“没有高光”仍允许正常瞳色。普通 LLM2 与 NAI `-r` 专用第二阶段都必须遵守这个省略状态。NAI 同一角色重复出现时，按逐实例 `source_text`（可含多条原文片段）及必要的 `anchor_id` 绑定修改，左格省略眼睛不影响右格；条件性基线只对可见、未被该实例修改的维度生效。

目标优先级为：

1. 用户明确的服装修改；
2. 用户明确的外貌修改；
3. 本次请求的命名套装或服装迁移；
4. 本次请求对应的角色服装变体 profile（casual、默认、夏季、冬季或舞台）；
5. 角色稳定外观 profile；
6. 最终 LLM 的自由补全。

例如：

- `官方默认服装，但是没穿外套`：保留默认套装其他部分，移除 `jacket`、`coat`、`cloak`、`cape` 等外套槽位。
- `官方默认服装，但是黑色外套`：将外套槽位替换为黑色。
- `官方常服，但是黑色系`：使用独立 casual 档案作为服装证据，并在其上应用用户的黑色系要求。
- `居家私服，但是黑色系`：不加载角色服装档案，由最终 LLM 设计黑色系居家私服。
- `千早爱音的裙子变蓝色`：没有给出新的基础服装，读取爱音 default 作为参考，并强制替换裙装颜色。
- `千早爱音穿羽丘夏季校服但没穿短裙`：以羽丘夏季校服为基础删除短裙，不读取爱音 default。
- `爱音穿连体式泳装，祥子穿分体式泳装`：两人都有实际服装基础，因此两份 default 都不加载；稳定外貌档案仍分别保留。
- `cosplay 重音 Teto，裙子消失，上衣撕破`：来源衣柜用于补全 Teto 造型；裙子从来源证据与允许集合中删除，上衣保留但标记为 `damage`，最终 Details 必须写出“无裙子”和“上衣撕破”的可见状态；Nltags 不再重复该句。
- `绑着粉色双钻头发型`：这是该角色发色、发型维度的显式 appearance 证据。第二阶段 LLM 对这两个维度的解释优先；未提及的瞳色等维度仍由角色档案约束，不能整段放弃 Identity 或混入服装来源角色的外貌。

## 已知不稳定点

当前角色级服装权限已经覆盖普通结构化路径。第一阶段负责建立角色、来源、修改之间的证据关系，第二阶段负责完整理解并形成最终画面；确定性代码只执行优先级和负面过滤。以下语义仍依赖第一阶段准确绑定目标角色：

- 服装补丁解析依赖明确的目标角色绑定。固定角色、服装迁移目标通常可绑定；仅靠自动语义识别的单角色请求可能没有绑定到补丁解析器。
- 当前补丁协议稳定支持移除、破损、颜色替换、全套改色、增加和仅保留指定槽位。`damage` 表示衣物仍然存在但破损，不能降级为 `remove`。
- LLM1 的标准槽位包含 `upper_body.primary / lower_body.skirt / one_piece.dress / outerwear / headwear / face_accessory.mask / handwear / legwear / footwear / lower_body.all / misc`。无法稳定分类的衣柜组件统一进入 `misc`；删除该槽位会阻止来源档案中的未分类组件继续注入，但不会把共享动作、场景或普通道具当作 `misc` 清除。具体删改对象仍由传给 LLM2 的原文证据决定。
- 第二阶段 LLM 仍可能写错，但它返回的 Tags、Details 和 Nltags 都会经过同一个 `WardrobeAuthority` 清理。已知旧衣柜组件可确定性删除；无法映射到任何已知档案或服装槽位的自由自然语言仍可能需要继续完善解析器。
- 本地衣柜仅提供当前构图可能可见的组件。裁剪复用通用 framing 分类，覆盖头部/脸部、上半身、cowboy shot、肚脐、下半身、腿/大腿/臀部、足部、手部和头部出框，也解析“只拍到腰部以上”等最低可见边界；既处理用户明确构图，也处理第二阶段最终选择的构图。画外组件不再以具体 tag 提示第二阶段，后置权限仍清理模型写出的复合修饰短语。裁剪只作用于继承的档案组件，用户明确补丁仍受保护；“下半身没穿”等衣物修改不会被误判成相机裁剪。
- 第一次 LLM 完全失败时，只会用本地已知角色恢复目标身份并标记 `explicit_but_unresolved`，用于禁止陈旧默认衣柜。若它已识别角色、却漏掉“角色穿着／换上……衣物”的直接关系，宿主也会禁止该角色恢复默认衣柜；本地确认的命名套组可绑定，其他衣物保留原文由第二阶段解释。仅在同句出现某角色名不足以判定穿着者。
- 外貌维度识别覆盖常见中英文发色、发型、瞳色、肤色、胸部尺寸与动物特征；极少见的自然语言外貌类别若尚未归入维度，会作为普通特征保留，不应被误当成服装槽位处理。

因此，当前仍不应把以下模糊表达当成完全确定性的补丁语法：

- `官方默认服装，但是黑色系`；
- 普通自动识别角色下的 `官方默认服装，但是没穿外套`。

## 后续改进方向

1. 将已本地确认的单一目标角色自动绑定为服装补丁对象。
2. 为“全套配色/风格”增加确定性 patch，而不是让 LLM 推断 `黑色系`。
3. 继续扩充删除、替换和 stale 组件的派生表达过滤；数据库服装仅作为 LLM2 上下文证据，不作为最终自动注入的可信下限。
4. 自由命名衣橱已实现，维护时继续区分所属角色、服装名称和学习来源（见下文）。

完整的 LLM1、角色数据库、衣柜、`WardrobeAuthority`、LLM2 与最终过滤关系见 [角色与服装配置工作流](角色与服装配置工作流.md)。


## 学习样本的归属与支持度

自动学习在写入档案前验证帖子的人数与来源。帖子必须有明确单人证据；`2girls`、`1girl 1boy`、`solo_focus` 等多人或歧义证据不能作为角色外貌和服装统计。角色标签必须包含目标；单人 persona 图可以同时标注人格与本名，但不能把“人数最少的角色标签组合”直接视为单人。Safebooru DAPI 没有独立角色分类字段，因此同时检查目标 tag 与单人证据。通用命名套组用独立来源类型采样，永远不输出角色外貌。

每个查询最多读取 3 页，每页最多 100 条；整次学习最多 12 个 HTTP 请求，并受约 20 秒请求预算约束。使用图片 MD5 或站点帖子 ID 对分页、镜像和重叠查询去重。初始聚类不足时继续带服装条件的锚点查询，仍不足则尝试单人检索；所有结果都必须继续满足 casual、summer、winter 或 stage 条件。不会把常服不足悄悄回退成 default，也不会用多人图凑数量。目标为收集 24 个可归属样本；最终服装聚类至少需要 6 个样本，否则返回 `*_evidence_insufficient`，不写入新服装或外貌。样本目标不是保证，帖子不足或网络失败必须保留为不足。

服装锚点优先区分具体学校制服，避免用泛化 `school_uniform` 把两所学校的制服混在一起；补样继续围绕原锚点。外貌使用稳定类别且要求超过半数样本支持，`hair_ribbon` 等服装配饰不进入外貌档案。这里只使用帖子标签证据，没有逐图视觉识别，不能据此宣称已确认官方设定。

证据保存 `sample_ids`（通过归属筛选的样本标识）、`queries`、`rejected_posts` 与 `request_errors`，并保留抓取、选中与聚类数量。已有编辑器档案仍遵循人工组件优先的规则：升级采样代码不会自动覆盖用户已修改的服装或外貌。旧的 3 样本档案需要在页面核对、修订；仅重载代码不会自动修好旧组件。
