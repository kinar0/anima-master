# 角色与服装配置工作流

本文说明当前提示词管线中与角色、外观和服装有关的数据源，重点解释配置页中仍然存在的新旧兼容入口，以及它们最终如何进入 Anima prompt。

## 总览

| 数据源 | 主要解决的问题 | 是否可绑定角色 | 最终用途 |
| --- | --- | --- | --- |
| `danbooru_character_alias_mappings` | 用户说的名字对应哪个 canonical 角色 tag | 是，形成角色 anchor | 角色身份识别与消歧 |
| `fixed_characters` | 原创、冷门或容易画错的角色有哪些稳定身份信息 | 取决于工作流 | 结构化路径中的身份提示；多人/旧路径中的较强约束 |
| 角色视觉档案 | 某角色或服装来源的稳定外观和服装组件是什么 | 是，保留目标 anchor | `Identity`、角色级 `Details`、重建后的 `Nltags` |
| 服装套组 | 某个完整命名套装对应哪个 canonical outfit tag | 是，形成 outfit anchor | 角色级完整套装约束，可附带验证过的组件档案 |
| 名词翻译 | 用户出现某个词时必须加入哪个 tag | 否 | 全局 hard tag |

## 当前提示词工作流

普通 `/anm` 优化请求大致经过以下步骤：

1. 从用户原文中匹配固定角色、角色别名、服装套组和名词翻译。
2. 第一阶段语义规划 LLM 提出目标角色、服装来源、命名套装、服装操作、动作和场景等候选。
3. 本地 `danbooru-tags` 校验候选；程序读取或学习角色视觉档案与套组视觉档案。
4. 每个目标角色得到一个 wardrobe 计划：`default_profile`、`casual_profile`、`named_outfit`、`outfit_source`、`creative_fallback` 或 `none`。
5. 如果用户没有提供任何服装证据，程序按 `unspecified_wardrobe_policy` 确定性地把临时计划改成 default 或 creative；不是让第一阶段 LLM 自行猜测。
6. 第二阶段 prompt writer 输出 `Count / Characters / Copyright / Identity / Details / Tags / Nltags`。
7. 后处理按角色重写 `Details`、过滤未验证服装、重建安全的角色服装 `Nltags`，再拼接质量词、画师词和共享 tags。

`Identity`、`Details` 和共享 `Tags` 的职责不同：

- `Identity` 保存角色固有外观。
- `Details` 保存带穿着者的动作、互动、道具和服装描述。
- `Tags` 是没有穿着者信息的共享 tag 区。
- `Nltags` 用于自然语言关系强化；服装部分必须来自已经过角色级后处理的 `Details`，不能信任第二阶段模型原始的共享服装叙述。

## 用户未说明服装时的策略

配置 key：`unspecified_wardrobe_policy`。

它只在用户没有提到具体衣物、命名套装、服装来源、默认/常服/私服选择或服装修改时生效。用户显式意图始终优先，配置不能把“穿白色睡衣长裙”改成默认服装，也不能把“默认服装”改成场景创作。

| 值 | 行为 |
| --- | --- |
| `scene_adaptive` | 推荐默认值。涩气模式或强场景词命中时使用 `creative_fallback`；其余未说明请求使用 `default_profile`。 |
| `default_profile` | 未说明时始终读取角色视觉档案中的 default 服装。 |
| `creative_fallback` | 未说明时始终由第二阶段模型为各角色设计服装。 |

`scene_adaptive_wardrobe_markers` 是可编辑的强场景词列表，采用不区分大小写的子串匹配。内置标记包括出浴、睡眠前后、运动/训练结束、比赛、健身、游泳结束和演出结束等。`比赛` 默认触发 creative，但“看比赛、观看比赛、观赛”等旁观语境会被排除。公园、在家、吃饭不会单独触发 creative。

当策略选择 `default_profile`，但目标角色没有可用的 default 服装组件时，程序会把该角色回退到 `creative_fallback`，而不是建立一个内容为空的 VERIFIED WARDROBE。显式要求“默认服装”时不会偷偷改成 creative；它仍按显式意图处理，方便从档案或查询证据中解决。

调试摘要中的 `wardrobe_source` 会记录本次来源，例如：

- `explicit_default_profile`、`explicit_casual_profile`、`explicit_named_outfit`、`explicit_clothing`、`explicit_creative`；
- `configured_default`、`configured_creative`、`scene_adaptive`；
- `missing_profile_fallback`。

第一阶段 LLM 对“没有服装信息”的角色只应输出临时 `none`；最终 default/creative 选择由上述主机侧规则决定。这避免了 LLM1 在同类请求中一会儿选择默认服装、一会儿自行设计。

## 上下文角色别名映射

配置 key：`danbooru_character_alias_mappings`。

格式：

```text
别名1 | 别名2=canonical_character_tag
```

例如：

```text
复仇者 | revenant=revenant_(elden_ring)
```

它只解决“是谁”，不保存该角色的详细外观或服装。带作品消歧后缀的角色必须在同一请求中命中兼容的 `danbooru_series_alias_mappings`，才会成为权威角色 anchor。

适合保存：

- 中文译名、俗称和罗马字别名；
- 容易被 LLM 拼错的 canonical character tag；
- 需要作品作用域消歧的角色。

不适合保存服装、动作或场景。

## 固定角色辅助信息

配置 key：`fixed_characters`。

格式：

```text
显示名=canonical 角色 tag 与稳定外观信息
```

例如：

```text
狐莉=original_character, 1girl, white_hair, red_eyes, fox_ears, fox_tail
长崎素世=nagasaki_soyo, long_brown_hair, blue_eyes
```

也可以使用聊天命令：

```text
/anm 添加角色 狐莉=original_character, 1girl, white_hair, red_eyes, fox_ears
```

### 匹配方式

只有用户原文包含左侧显示名时才命中。当前是直接的原始子串匹配；出现“不要角色”“无人”等特殊标记时会关闭固定角色命中。

### 不同路径中的真实作用

| 路径 | `fixed_characters` 的作用 |
| --- | --- |
| 普通七字段结构化路径 | 作为本地角色身份辅助信息发给第二阶段模型；用于匹配结构化 roster，但不保证右侧每一个词都被逐项 hard 注入 |
| `/anm 多人` 兼容路径 | 按人物块较强地注入；`1girl`、`1boy`、`solo` 等单人计数词会从人物外观块移除，性别信息仍参与总人数计算 |
| 旧平铺/非结构化回退 | 第一个命中的固定角色整串进入最终 prompt，并清理竞争性身份 tags |
| `/anm 无优化`、原样模式或关闭优化 | 不参与，原始 prompt 直接发送 |

因此旧描述“提到角色名时直接拼接该角色 tags”只对多人兼容路径和旧回退路径完全成立，对当前普通结构化路径并不准确。

### 应保存的内容

- canonical 角色 tag，已知时建议放在第一项；
- 原创角色标识；
- 性别与稳定年龄感；
- 发色、瞳色、种族；
- 耳朵、尾巴、角、翅膀；
- 不随服装变化的标志性身体或身份特征。

### 不应保存的内容

- 默认服装、校服、演出服或私服；
- 本次动作、表情或场景；
- 质量词、画师词和画风词；
- 多人关系和仅在某次请求成立的状态。

把服装放入 `fixed_characters` 会绕过或干扰当前 wardrobe 优先级：普通结构化路径可能把它误当固有身份，多人路径可能直接注入，旧回退路径则会整串全局注入。

## 角色视觉档案

页面位置：`服装词库 → 角色视觉档案`。内部主要保存 `character_outfit` profile。

一条档案包含：

- 档案名称和触发别名；
- `sourceTags`：角色或服装来源 canonical tags；
- `tags`：从帖子样本学习或人工填写的服装组件；
- `appearanceTags`：稳定发色、瞳色、角、耳朵、尾巴等；
- `qualifier`：`default / casual / summer / winter / stage`；
- 采样模式、样本数、更新时间等证据。

非默认变体使用独立记录，避免夏季、冬季、演出服和官方常服互相覆盖。

### 使用方式

- `default_profile` 使用角色默认视觉档案。
- `casual_profile` 使用官方 casual 档案。
- `named_outfit` 使用命名套组 tag，并可附带该套组的帖子组件档案。
- `outfit_source` 使用来源角色或人格的可迁移服装档案。
- `creative_fallback` 不注入默认/常服档案，只保留稳定外观，让第二阶段模型设计本次衣服。

当前语义中，“官方常服/常服/casual outfit”选择 `casual_profile`；“私服/居家私服/居家服/休闲穿搭”选择 `creative_fallback`，两者不是同义词。

### 最终注入

- `appearanceTags` 追加到对应角色的 `Identity`。
- 有效服装 tags 在应用用户增删、换色等补丁后，写入对应角色的 `Details`。
- `9a79e94` 起，后处理会从校正后的 `Details` 重建带角色名的服装 `Nltags`。
- 单个已验证角色的服装 tags 可以进入共享 tag 区强化。
- 多个角色只把所有角色共同拥有的服装 tags 放入共享区；各自不同的服装只保留在带穿着者的 `Details + Nltags`。
- 只要存在 `creative_fallback` 角色，程序不会自动把其他角色的已验证服装全局化，避免创意角色吸收他人衣服。
- 所有可见角色都是 creative 时，第二阶段模型可以在共享 `Tags` 中输出真正适用于全员的普通服装 tags；各角色不同的衣物仍只能写在各自 `Details`。
- verified 与 creative 混合时，共享 `Tags` 继续使用严格白名单；creative 角色依靠带名字的 `Details` 表达衣服，避免吸收 verified 角色的套装。
- creative 共享 Tags 仍会删除校服/制服和裸露状态，避免模型凭空发明命名校服或绕过服装权限。

## 服装套组与兼容配置入口

页面位置：`服装词库 → 服装套组`。

配置 key：`danbooru_named_outfit_mappings`。普通配置页中的“服装套组映射（兼容配置入口）”和页面里的服装套组是同一系统，不是两套功能。

格式：

```text
别名1 | 别名2 | 别名3=canonical_outfit_tag
```

例如：

```text
月之森校服 | 月之森制服 | tsukinomori school uniform=tsukinomori_school_uniform
```

命中后程序创建 `role=outfit` 的语义 anchor。语义规划通过 `named_outfit + anchor_id` 把完整套组绑定给具体目标角色。若存在该套组的视觉档案，会同时使用验证过的组件；没有组件档案时，仅使用完整 canonical 套组 tag，不让第二阶段模型自行猜测衬衫、裙子、鞋袜等组成。

### 为什么配置默认只有月之森校服

`月之森校服=tsukinomori_school_uniform` 是该功能加入时留下的一条历史种子，不是完整服装列表，也不是程序唯一支持的套组。

套组有两类来源：

- 手动套组保存在 `danbooru_named_outfit_mappings`，会显示在普通配置页；
- 自动学习套组保存在视觉档案缓存，标记为 `origin=learned`，通常只在服装词库页面显示。

因此普通配置页可能只有一个月之森条目，而服装词库页面有更多自动学习套组。该默认项可以删除；删除只会移除这条手动种子，已有自动学习记录仍可能继续命中。

### 安全限制

- 自动学习不会把泛化的 `school_uniform` 或 `uniform` 保存成某个专名校服。
- 手动配置优先于冲突的自动学习别名。
- 不同套组实体可以指向同一个 canonical tag；匹配时仍保留各自别名和变体 anchor，最终 hard tag 会去重。
- 正常结构化路径可以绑定穿着者；如果角色计划构建失败，才可能退化为无归属的全局套组 tag。

## 名词翻译

页面位置：`服装词库 → 名词翻译`。

配置 key：`danbooru_term_mappings`。

格式：

```text
中文名词或触发词=canonical_tag
```

例如：

```text
舞会面具=masquerade_mask
芭蕾舞裙=tutu
白丝袜=white_pantyhose
```

从提交 `05577f7` 开始，名词翻译只有这一处配置/页面数据源，不再另有代码内置映射。

### 当前行为

程序把用户原文转小写后执行简单子串命中。命中结果直接进入 `confirmed_tags`，不经过第二阶段模型，也不再联网验证，然后作为全局 hard tag 和服装清理白名单的一部分。

它没有保存：

- 穿着者；
- 语义角色；
- 服装槽位；
- 否定状态；
- 作品或角色作用域。

所以它适合道具、场景、材质、普通视觉概念和单人请求中的明确衣物；不适合多人场景里只属于其中一个角色的服装或配饰。

例如：

```text
爱音穿芭蕾舞裙，祥子穿西装
```

`tutu` 仍是全局 tag，理论上可能污染祥子。需要角色归属的完整套装应使用服装套组；普通衣物若需要稳定的多人归属，则还需要未来的角色级名词绑定数据结构。

## 服装优先级

当前设计目标为：

1. 用户本次明确的服装增删、换色和保留操作；
2. 本次指定的命名套组或服装迁移来源；
3. 对应角色和变体的视觉档案；
4. 角色稳定外观档案；
5. `creative_fallback` 中第二阶段模型对未指定服装槽位的补全。

需要注意，名词翻译是全局 hard tag 快捷入口，并不天然服从角色级优先级；`fixed_characters` 在多人和旧回退路径中也可能较强地注入。因此不要用这两个入口长期保存角色专属服装。

## 推荐配置分工

| 需求 | 推荐入口 |
| --- | --- |
| 中文角色名对应 Danbooru 角色 | 上下文角色别名映射 |
| 原创/冷门角色的稳定身份 | 固定角色辅助信息 |
| 角色默认服装、官方常服和稳定外观 | 角色视觉档案 |
| 有专名的完整校服、演出服或套装 | 服装套组 |
| 无需绑定人物的道具、场景、材质或普通 hard tag | 名词翻译 |

## 维护注意事项

- 服装词库页面保存使用 revision 乐观锁，避免覆盖其他会话刚写入的档案。
- 页面保存后运行时配置与缓存立即更新；安装或更新页面代码后才需要重载插件。
- `fixed_characters`、名词翻译和中文套组别名目前均包含不同程度的子串匹配，应避免过短或容易出现在普通句子中的触发词。
- 修改角色计划、服装清理器、结构化字段职责或最终 prompt 拼接顺序时，应同时更新本文。
