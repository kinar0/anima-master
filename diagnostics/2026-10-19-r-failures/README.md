## 根因一：结构解析错误绕过了一次修复机会（5 条）

`nai_character_mode.py:607` 直接解析 JSON，615 行严格检查 `viewpoint/layout/relations`，634 行读取 `x/y`。这些检查是合理的提交前契约。

问题在调用顺序：`prompt_pipeline.py:5813` 先调用解析器，5825 行以后才根据身份/文字错误进入一次修复。前述解析器抛出的异常直接落到函数末尾的统一失败分支，根本不会进入修复。因此同一 writer 虽然已有修复机制，却只覆盖“能先解析成功”的回复。这五条实际均只有一次 LLM2 调用。

两个 JSON 案例离线仅移除各自两处多余右花括号就能完整解析，确认是内部语法破坏。另三个是字段缺失或键名漂移，不能笼统称作“没有构图分析”“坐标超范围”。保存任务书中的 schema 本来要求这些字段，现有调用没有通过这里的参数强制 JSON schema 输出。

没有保存逐调用 finish_reason/usage，不能证明模型为何产生这些错误，更不能认定为 token 预算耗尽。现存回复错误位于内部且末尾闭合，证据不支持把这两个案例直接归因于截断。

## 根因二：身份审核混用了“有档案”与“身份已确认”（4 条）

`prompt_pipeline.py:3803` 的 `nai_local_identity_mentions` 从角色外貌档案和服装档案恢复名字，并要求唯一 owner；它并非全部已确认身份的清单。

但 `review_nai_identities` 对模型返回的每一条 `identity_review` 都执行 3929 行的名单匹配，3934 行的 `not matching` 直接判错。报错合并为“known identity and exact contextual evidence”，掩盖了究竟是名单还是引用的问题。

因此出现两个可重复的分支：

1. 查询已经确认身份，但该人物没有本地档案。14:20 的 `togawa_sakiko` 和 18:14 的 `misumi_uika` 都属于这一类；它们在 `confirmed_character_bindings` 内，却不在 `nai_identity_mentions` 内。
2. 人物仍未解析。14:22 的“祥祥”和 18:28 的“初华”也不在名单；模型额外输出审核行，会使原本可按未知/原文身份处理的角色或引用变成硬失败。

四个案例的初稿、修复稿审核引用都真实存在于原文，所以反复要求模型“引用准确原文”解决不了 `not matching`。此前已有“无效但多余的 visible 审核只作诊断”的兼容，也要求 `matching` 成立，因此不能覆盖此分支。

离线重建保存的身份输入后，四条的错误都与记录一致；仅在内存中移除不在该名单的额外审核行，身份错误即消失。这是定位否决条件的对照，不是建议直接删除所有审核或放过缺人：14:20 仍有独立文字错误；必要的缺人解释、来源人物出场、矛盾分类和新权限仍须保留校验。

1. 将 JSON、必填字段和坐标等结构错误纳入现有一次有界修复，与身份/文字共用预算。保留严格解析，不按角色、句子、某个衣物名称或某一种花括号错误写临时补丁，也不由主机猜坐标。
